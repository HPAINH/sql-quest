Этот уровень — фундамент. Здесь ты научишься доставать данные из одной таблицы, выбирать нужные колонки, давать им понятные имена, сортировать выдачу и отрезать от неё нужный кусок. Все запросы ниже работают на той же базе ShopData, что и тикеты: нажми «Выполнить» под любым примером, чтобы увидеть результат, или отправь его в песочницу и поменяй под себя.

## Таблицы, строки и колонки

Реляционная база данных хранит информацию в **таблицах**. Таблица похожа на лист Excel со строгими правилами:

- у каждой **колонки** есть имя и тип: целое число, деньги, текст, дата, логическое значение;
- каждая **строка** — один объект: один клиент, один заказ, один товар;
- порядок строк в таблице не определён — база хранит их так, как ей удобно;
- у большинства таблиц есть **первичный ключ** — колонка (или набор колонок), значение которой уникально для каждой строки: `customer_id`, `order_id`.

Таблицы связаны между собой через ключи. Колонка `orders.customer_id` хранит номер клиента из `customers.customer_id` — это **внешний ключ**. Благодаря этому одного клиента не нужно копировать в каждый его заказ: достаточно сослаться на его номер.

### Что лежит в ShopData

| Таблица | Одна строка — это | Ключ |
| --- | --- | --- |
| `customers` | клиент магазина | `customer_id` |
| `orders` | заказ | `order_id` |
| `order_items` | позиция заказа: товар, количество, цена | `order_id` + `product_id` |
| `products` | товар каталога | `product_id` |
| `categories` | категория, у подкатегорий есть `parent_id` | `category_id` |
| `payments` | платёж по заказу | `payment_id` |
| `deliveries` | отгрузка и вручение заказа | `order_id` |
| `reviews` | отзыв о товаре | `review_id` |
| `promo_codes`, `order_promos` | промокоды и их применение | `code`, `order_id` |
| `employees` | сотрудник, у него есть руководитель `manager_id` | `employee_id` |
| `warehouses`, `stock` | склады и остатки на них | `warehouse_id`, пара склад + товар |
| `events` | событие на сайте: просмотр, корзина, оформление, покупка | `event_id` |
| `ab_assignments` | клиент в группе A/B-теста | клиент + эксперимент |
| `product_embeddings` | вектор товара для поиска похожих | `product_id` |

Полное описание колонок есть на экране каждого тикета (блок «Таблицы» и кнопка «Вся схема») и в песочнице. Данные заканчиваются **30 июня 2026 года** — в тикетах «сегодня» означает 1 июля 2026.

> **Совет.** Прежде чем писать отчёт, посмотри на таблицу глазами: `SELECT * FROM таблица LIMIT 10`. Пять секунд разведки экономят полчаса отладки — сразу видно, какие там значения, есть ли NULL, в каком формате даты.

## SELECT и FROM

Любой запрос на чтение начинается с двух частей: **что** взять и **откуда**.

```sql
SELECT name, price
FROM products;
```

- `SELECT` перечисляет колонки результата через запятую. Порядок колонок в результате — такой, как ты их написал.
- `FROM` называет таблицу-источник.
- Точка с запятой в конце отделяет команды друг от друга. Для одного запроса она не обязательна, но привычка ставить её полезна.

Звёздочка `*` означает «все колонки в том порядке, в каком они объявлены в таблице»:

```sql
SELECT *
FROM warehouses;
```

`SELECT *` удобен, чтобы осмотреться, но в отчётах и в коде его избегают: если в таблицу добавят колонку, результат молча изменится, а лишние колонки замедляют передачу данных.

### Регистр и пробелы

SQL не различает регистр ключевых слов и имён: `select`, `SELECT` и `Select` — одно и то же, `FROM products` и `from PRODUCTS` найдут одну таблицу. Принято писать ключевые слова заглавными, а имена — строчными: так запрос читается быстрее.

Переносы строк и отступы тоже не важны для базы — они нужны людям. Удобный стиль: каждая часть запроса с новой строки, длинные списки колонок — по одной на строку.

```sql
SELECT product_id,
       name,
       brand,
       price
FROM products
ORDER BY price DESC
LIMIT 5;
```

### Комментарии

Всё после `--` до конца строки — комментарий, база его пропускает. Многострочный комментарий пишется в `/* … */`.

```sql
-- самые дорогие товары
SELECT name, price   -- только две колонки
FROM products
ORDER BY price DESC
LIMIT 3;
```

## Псевдонимы колонок

Результат запроса — новая таблица, и её колонкам можно дать другие имена. Это делает слово `AS`:

```sql
SELECT name AS product,
       price AS price_rub,
       cost AS cost_rub
FROM products
LIMIT 5;
```

`AS` можно опустить — `price price_rub` сработает так же, — но тогда легко перепутать псевдоним с забытой запятой. Пиши `AS` всегда.

Если имя должно содержать пробел, заглавные буквы или кириллицу в «строгом» виде, его берут в **двойные кавычки**:

```sql
SELECT name AS "Товар", price AS "Цена, ₽"
FROM products
LIMIT 3;
```

> **Не путай.** Двойные кавычки `"…"` — это имя (колонки, таблицы, псевдонима). Одинарные `'…'` — это текстовое значение. `"Москва"` для PostgreSQL означает колонку с именем Москва, а `'Москва'` — строку текста.

Псевдонимы особенно нужны, когда колонка вычисляется. Без имени PostgreSQL назовёт её как придётся — `?column?` или по имени функции:

```sql
SELECT name,
       price - cost AS margin
FROM products
LIMIT 5;
```

Про вычисления подробно поговорим на уровне 2, а пока запомни: у каждой колонки результата должно быть осмысленное имя.

## Сортировка: ORDER BY

Без сортировки порядок строк в результате **не гарантирован**. Сегодня он может совпасть с порядком вставки, а завтра, после обновления статистики или параллельного выполнения, — нет. Если порядок важен, его нужно задать явно.

```sql
SELECT name, price
FROM products
ORDER BY price;
```

- `ASC` — по возрастанию, это вариант по умолчанию;
- `DESC` — по убыванию.

```sql
SELECT name, price
FROM products
ORDER BY price DESC;
```

### Несколько ключей

Можно сортировать по нескольким колонкам: сначала по первой, а внутри одинаковых значений первой — по второй, и так далее. Направление задаётся для каждой колонки отдельно.

```sql
SELECT department, full_name, salary
FROM employees
ORDER BY department, salary DESC;
```

Здесь отделы идут по алфавиту, а внутри отдела сотрудники — от большей зарплаты к меньшей.

> **Ловушка.** `DESC` относится только к той колонке, после которой написан. `ORDER BY department, salary DESC` — это «отдел по возрастанию, зарплата по убыванию», а не «всё по убыванию».

### Сортировка по псевдониму и по выражению

В `ORDER BY` можно использовать псевдоним из `SELECT` и любое выражение:

```sql
SELECT name, price - cost AS margin
FROM products
ORDER BY margin DESC
LIMIT 5;
```

Можно сортировать и по колонке, которой нет в результате: `ORDER BY created_at` при `SELECT name`. Ещё есть сортировка по номеру колонки — `ORDER BY 2 DESC`, — но в рабочем коде её избегают: при правке списка колонок номер начинает указывать не туда.

### Где оказываются NULL

`NULL` — это «значение неизвестно». При сортировке PostgreSQL считает NULL **больше любого значения**: при `ASC` они в конце, при `DESC` — в начале. Это поведение можно поменять:

```sql
SELECT first_name, last_name, birth_date
FROM customers
ORDER BY birth_date DESC NULLS LAST
LIMIT 5;
```

Без `NULLS LAST` первыми шли бы клиенты без даты рождения — для отчёта «самые молодые клиенты» это явно не то.

## LIMIT и OFFSET

`LIMIT n` оставляет первые n строк результата, `OFFSET k` пропускает первые k.

```sql
SELECT order_id, created_at, amount
FROM orders
ORDER BY amount DESC
LIMIT 5;
```

```sql
SELECT order_id, created_at, amount
FROM orders
ORDER BY amount DESC
LIMIT 5 OFFSET 5;
```

Второй запрос возвращает «вторую пятёрку» — строки с 6-й по 10-ю. Так устроена **постраничная выдача**: страница номер p размером n — это `LIMIT n OFFSET (p − 1) × n`.

Стандарт SQL записывает то же самое длиннее, PostgreSQL понимает оба варианта:

```sql
SELECT order_id, amount
FROM orders
ORDER BY amount DESC
OFFSET 0 ROWS
FETCH FIRST 3 ROWS ONLY;
```

### LIMIT без ORDER BY — лотерея

`LIMIT` берёт первые строки **того порядка, который получился**. Если порядок не задан, «первые 10 заказов» — это просто какие-то 10 заказов. Запрос может возвращать разное от запуска к запуску, и проверка в игре это поймает.

### Ничьи на границе

Допустим, нужны 3 самых дешёвых товара, а четыре товара стоят одинаково. Какие три из них попадут в выдачу — не определено. Поэтому к сортировке добавляют **тай-брейкер** — колонку, которая гарантированно различает строки, обычно ключ:

```sql
SELECT product_id, name, price
FROM products
ORDER BY price, product_id
LIMIT 3;
```

> **Совет.** Если сортировка идёт по неуникальной колонке, а дальше стоит `LIMIT` или `OFFSET`, добавь в конец `ORDER BY` первичный ключ. Тогда результат детерминирован: одинаковый при каждом запуске.

PostgreSQL умеет и обратное — забрать всех, кто делит последнее место: `FETCH FIRST 3 ROWS WITH TIES`.

```sql
SELECT name, price
FROM products
ORDER BY price
FETCH FIRST 3 ROWS WITH TIES;
```

## DISTINCT: уникальные значения

`DISTINCT` убирает из результата повторяющиеся строки.

```sql
SELECT DISTINCT city
FROM customers
ORDER BY city;
```

Если колонок несколько, уникальной должна быть **комбинация** значений, а не каждая колонка по отдельности:

```sql
SELECT DISTINCT status, delivery_city
FROM orders
ORDER BY delivery_city, status
LIMIT 12;
```

Строки «delivered, Москва» и «cancelled, Москва» обе останутся — комбинации разные.

> **Ловушка.** `DISTINCT` относится ко всей строке результата, а не к первой колонке после него. `SELECT DISTINCT city, first_name` не даст «по одному клиенту из каждого города» — он даст все уникальные пары город + имя. Задачу «одна строка на группу» решают иначе — оконными функциями или `DISTINCT ON` (уровень 7).

Для `DISTINCT` все `NULL` считаются одинаковыми: сколько бы клиентов ни было без даты рождения, в `SELECT DISTINCT birth_date` будет ровно одна строка с NULL.

`DISTINCT` — быстрый способ узнать, какие значения вообще встречаются в колонке. Например, какие службы доставки работают с магазином:

```sql
SELECT DISTINCT courier
FROM deliveries
ORDER BY courier;
```

## Как PostgreSQL читает запрос

Мы пишем части запроса в одном порядке, а база выполняет их в другом. Это объясняет многие «странности» SQL.

| Порядок записи | Порядок выполнения |
| --- | --- |
| 1. `SELECT` | 1. `FROM` — какая таблица |
| 2. `FROM` | 2. `WHERE` — какие строки оставить (уровень 1) |
| 3. `WHERE` | 3. `GROUP BY` и `HAVING` — группировка (уровень 3) |
| 4. `ORDER BY` | 4. `SELECT` — вычислить колонки и псевдонимы |
| 5. `LIMIT` / `OFFSET` | 5. `DISTINCT` — убрать повторы |
|  | 6. `ORDER BY` — отсортировать |
|  | 7. `OFFSET` и `LIMIT` — отрезать кусок |

Отсюда следствия:

- псевдоним из `SELECT` можно использовать в `ORDER BY` — к моменту сортировки он уже вычислен;
- `LIMIT` применяется **после** сортировки, поэтому «топ-5» работает;
- псевдоним нельзя использовать в `WHERE` — фильтрация происходит раньше, чем он появляется (это встретится на следующем уровне).

## Типичные ошибки

### Забытая запятая

```sql
SELECT name price, brand
FROM products
LIMIT 3;
```

Этот запрос выполнится без ошибки — и это хуже ошибки. `name price` PostgreSQL прочитает как «колонка name с псевдонимом price». В результате две колонки вместо трёх, и первая называется price, хотя в ней названия товаров. Выполни пример и посмотри на заголовки колонок.

### Опечатка в имени

Опечатку в имени колонки база, наоборот, поймает сразу:

```sql-error
SELECT nmae, price
FROM products;
```

PostgreSQL отвечает `column "nmae" does not exist` и часто подсказывает похожее имя. Игра переводит такие сообщения на русский и объясняет, что пошло не так.

### Текст в двойных кавычках

```sql-error
SELECT name AS 'Товар'
FROM products;
```

Псевдоним — это имя, поэтому кавычки должны быть двойными: `AS "Товар"`.

### Сортировка по тексту вместо числа

Если число хранится как текст, сортировка будет алфавитной: `'100' < '20'`, потому что символ «1» меньше «2». В ShopData деньги и количества хранятся в числовых типах, но при импорте реальных данных это частая беда.

### Ожидание порядка без ORDER BY

«Он же всегда возвращал по порядку» — до первого обновления версии, роста таблицы или параллельного плана. Нужен порядок — пиши `ORDER BY`.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Все колонки таблицы | `SELECT * FROM t` |
| Нужные колонки | `SELECT a, b FROM t` |
| Переименовать колонку | `SELECT a AS new_name` |
| Имя с пробелом | `SELECT a AS "Моя колонка"` |
| По возрастанию / убыванию | `ORDER BY a` / `ORDER BY a DESC` |
| Несколько ключей | `ORDER BY a, b DESC` |
| NULL в конце | `ORDER BY a DESC NULLS LAST` |
| Первые n строк | `ORDER BY … LIMIT n` |
| Страница p по n строк | `LIMIT n OFFSET (p − 1) * n` |
| Все, кто делит последнее место | `FETCH FIRST n ROWS WITH TIES` |
| Уникальные значения | `SELECT DISTINCT a FROM t` |
| Уникальные комбинации | `SELECT DISTINCT a, b FROM t` |

## Проверь себя

?? Что вернёт `SELECT DISTINCT status FROM orders` — сколько строк?
:: Столько, сколько разных статусов встречается в заказах. В ShopData их шесть: new, paid, shipped, delivered, cancelled, returned. Проверь: выполни запрос в песочнице.

?? Почему `SELECT name FROM products LIMIT 5` может возвращать разные товары?
:: Потому что без `ORDER BY` порядок строк не определён, и «первые пять» — это любые пять. Добавь сортировку и тай-брейкер, например `ORDER BY price DESC, product_id`.

?? Как получить 11–20 самых дорогих товаров?
:: `ORDER BY price DESC, product_id LIMIT 10 OFFSET 10`. OFFSET пропускает первые десять, LIMIT берёт следующие десять.

?? В чём разница между `ORDER BY a, b DESC` и `ORDER BY a DESC, b DESC`?
:: В первом случае `a` сортируется по возрастанию, а `b` по убыванию внутри одинаковых `a`. Во втором обе колонки по убыванию. `DESC` действует только на ту колонку, после которой стоит.

?? Где окажутся строки с NULL при `ORDER BY birth_date`?
:: В конце: PostgreSQL считает NULL больше любого значения. При `DESC` они окажутся в начале. Поменять можно через `NULLS FIRST` и `NULLS LAST`.

?? Можно ли написать `ORDER BY margin`, если `margin` — псевдоним из SELECT?
:: Да. ORDER BY выполняется после SELECT, поэтому псевдонимы ему уже известны.
