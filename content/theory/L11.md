Последний уровень — о том, что отличает Lead-аналитика: понимать, **как** база выполняет запрос, и уметь сделать его быстрым; собирать данные для моделей так, чтобы модель не обманывала саму себя; искать похожие объекты по векторам прямо в PostgreSQL. На маленькой базе ShopData запросы и так выполняются за миллисекунды, но планы и стоимости честные — те же механизмы на таблице в сто миллионов строк решают, будет отчёт строиться секунду или час.

## Как PostgreSQL выполняет запрос

SQL — декларативный язык: ты описываешь, **что** хочешь получить, а не **как**. Путь от текста до результата:

1. **Разбор** — текст превращается в дерево, проверяются имена таблиц и колонок.
2. **Переписывание** — раскрываются представления, правила.
3. **Планирование** — оптимизатор перебирает способы выполнить запрос: в каком порядке соединять таблицы, читать ли таблицу целиком или через индекс, каким алгоритмом соединять. Для каждого варианта он оценивает **стоимость** и выбирает самый дешёвый.
4. **Выполнение** — исполнитель идёт по выбранному плану.

Оценки стоимости строятся на **статистике**: сколько строк в таблице, сколько разных значений в колонке, какие самые частые, как распределены. Статистику собирает команда `ANALYZE` (и автоматический autovacuum). Если статистика устарела, планировщик ошибается в оценках и выбирает плохой план.

## EXPLAIN: читаем план

`EXPLAIN` показывает план, не выполняя запрос. Кнопка «Показать план» под примером строит его прямо здесь.

```sql-plan
EXPLAIN
SELECT c.city, COUNT(*) AS orders_cnt
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
GROUP BY c.city;
```

План — дерево. Читать его нужно **снизу вверх и изнутри наружу**: листья — чтение таблиц, выше — соединения, агрегация, сортировка. Каждый узел передаёт строки родителю.

В текстовом виде у каждого узла есть оценки:

```text
Hash Join  (cost=79.00..243.78 rows=6000 width=18)
```

| Поле | Смысл |
| --- | --- |
| `cost=79.00..243.78` | стоимость до первой строки и стоимость всех строк, в условных единицах |
| `rows=6000` | сколько строк узел, по оценке, вернёт |
| `width=18` | средний размер строки в байтах |

Единица стоимости примерно равна чтению одной страницы диска последовательно. Абсолютное значение мало что говорит — **сравнивай стоимости вариантов одного и того же запроса**. В задачах на оптимизацию игра так и делает: стоимость твоего плана сравнивается со стоимостью исходного.

### EXPLAIN ANALYZE

`EXPLAIN ANALYZE` **выполняет** запрос и добавляет к оценкам реальные числа: время каждого узла, фактическое число строк, число повторов (`loops`). Главное, на что смотреть, — расхождение оценки `rows` и фактического числа строк. Если планировщик ждал 10 строк, а пришло 100 000, план почти наверняка неудачный, и причина — статистика или условие, которое планировщик не умеет оценить.

> **Осторожно.** `EXPLAIN ANALYZE` для `UPDATE` или `DELETE` действительно меняет данные. Оборачивай такой анализ в транзакцию с `ROLLBACK`.

## Способы чтения таблицы

| Узел | Как работает | Когда выгоден |
| --- | --- | --- |
| `Seq Scan` | читает всю таблицу подряд | нужна большая часть строк или таблица маленькая |
| `Index Scan` | идёт по индексу и для каждой найденной записи читает строку из таблицы | нужно мало строк |
| `Index Only Scan` | берёт всё нужное прямо из индекса, таблицу не читает | все колонки запроса есть в индексе |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | сначала собирает по индексу «карту» нужных страниц, потом читает их по порядку | строк средне много: больше, чем для Index Scan, меньше, чем для Seq Scan |

`Seq Scan` — не всегда плохо. Если нужна половина таблицы, прочитать её подряд дешевле, чем прыгать по индексу. Плохо, когда `Seq Scan` читает миллионы строк, чтобы найти десяток.

### Способы соединения

| Узел | Как работает | Когда выгоден |
| --- | --- | --- |
| `Nested Loop` | для каждой строки внешней таблицы ищет пары во внутренней | внешняя таблица маленькая, по внутренней есть индекс |
| `Hash Join` | строит хеш-таблицу по меньшей стороне, потом проходит по большей | большие таблицы, условие равенства |
| `Merge Join` | сливает две отсортированные последовательности | обе стороны уже отсортированы (например, по индексу) |

## Индексы

**Индекс** — отдельная структура, которая позволяет быстро найти строки по значению колонки, не читая всю таблицу. Как алфавитный указатель в конце книги: чтобы найти «JOIN», не нужно листать все страницы.

Основной тип индекса в PostgreSQL — **B-tree**: сбалансированное дерево, в котором значения хранятся отсортированными. Он ускоряет:

- равенство: `customer_id = 44`;
- диапазоны: `created_at >= … AND created_at < …`, `BETWEEN`;
- сортировку: `ORDER BY created_at DESC LIMIT 10` — можно просто пройти по индексу с конца;
- `LIKE 'префикс%'` (при подходящей настройке индекса).

```sql
CREATE INDEX events_session_idx ON events (session_id);

EXPLAIN SELECT * FROM events WHERE session_id = 7;
```

Без индекса этот запрос читал бы все события. С индексом — находит нужные за несколько шагов.

```sql-plan
EXPLAIN
SELECT order_id, created_at, amount
FROM orders
ORDER BY created_at DESC
LIMIT 10;
```

`Index Scan Backward` — PostgreSQL прочитал индекс по `created_at` с конца и остановился после десяти строк, не сортируя всю таблицу.

### Цена индексов

Индексы не бесплатны:

- занимают место на диске;
- **замедляют запись**: каждый `INSERT`, `UPDATE` и `DELETE` обновляет все индексы таблицы;
- без пользы, если колонка почти не фильтрует (например, флаг, у которого 95% строк — `true`).

Поэтому индексы создают под конкретные частые запросы, а не «на всякий случай» на каждую колонку.

## Sargable: когда индекс может помочь

Условие называют **sargable** (Search ARGument ABLE), если колонка в нём стоит «как есть» и индекс можно использовать. Если к колонке применена функция или приведение типа, обычный индекс по колонке бесполезен: в нём лежат значения колонки, а не результат функции.

Сравни два способа выбрать заказы за один день:

```sql-plan
EXPLAIN
SELECT order_id, amount
FROM orders
WHERE created_at::date = '2026-06-15';
```

```sql-plan
EXPLAIN
SELECT order_id, amount
FROM orders
WHERE created_at >= '2026-06-15'
  AND created_at <  '2026-06-16';
```

Результат одинаковый, а планы разные: в первом случае `Seq Scan` по всей таблице с вычислением `::date` для каждой строки, во втором — `Index Scan` по диапазону. Стоимость отличается в десятки раз.

| Не sargable | Sargable |
| --- | --- |
| `created_at::date = '2026-06-15'` | `created_at >= '2026-06-15' AND created_at < '2026-06-16'` |
| `EXTRACT(YEAR FROM created_at) = 2025` | `created_at >= '2025-01-01' AND created_at < '2026-01-01'` |
| `date_trunc('month', created_at) = '2026-06-01'` | `created_at >= '2026-06-01' AND created_at < '2026-07-01'` |
| `customer_id::text = '44'` | `customer_id = 44` |
| `price * 1.2 > 1000` | `price > 1000 / 1.2` |
| `lower(email) = '…'` | индекс по выражению `lower(email)` |

```sql-plan
EXPLAIN
SELECT *
FROM orders
WHERE customer_id::text = '44';
```

Приведение типа выглядит безобидно, но выключает индекс по `customer_id`. Такие условия часто появляются, когда идентификатор пришёл строкой из внешней системы.

### Индекс по выражению

Если без функции не обойтись — например, почту надо искать без учёта регистра, — создают индекс **по выражению**. Тогда условие с тем же выражением снова становится sargable:

```sql
CREATE INDEX customers_email_lower_idx ON customers (lower(email));
ANALYZE customers;

EXPLAIN SELECT customer_id FROM customers WHERE lower(email) = 'aleksey.nikolaev@mail.ru';
```

Выражение в запросе должно **точно** совпадать с выражением индекса: индекс по `lower(email)` не поможет условию `upper(email) = …`.

## Составные, частичные и покрывающие индексы

### Составной индекс

Индекс по нескольким колонкам `(a, b)` отсортирован сначала по `a`, внутри — по `b`. Как телефонный справочник: по фамилии, потом по имени. Отсюда правило **левого префикса**:

| Условие | Индекс `(customer_id, created_at)` помогает? |
| --- | --- |
| `customer_id = 44` | да |
| `customer_id = 44 AND created_at >= '2026-01-01'` | да, идеально |
| `customer_id = 44 ORDER BY created_at DESC` | да, и сортировка бесплатна |
| `created_at >= '2026-01-01'` | почти нет — первая колонка не задана |

Порядок колонок важен: первой ставь ту, по которой фильтруешь на равенство, следом — диапазонную или сортировочную.

### Частичный индекс

Индекс можно построить только по части строк — тем, которые реально ищут:

```sql
CREATE INDEX orders_open_idx ON orders (created_at) WHERE status IN ('new', 'paid');

EXPLAIN
SELECT order_id, created_at FROM orders
WHERE status IN ('new', 'paid') AND created_at >= '2026-06-25';
```

Открытых заказов мало, поэтому индекс маленький и быстрый, а запись остальных заказов его не трогает.

### Покрывающий индекс

Если все колонки запроса есть в индексе, PostgreSQL может вообще не обращаться к таблице — `Index Only Scan`. Дополнительные колонки, по которым не ищут, добавляют через `INCLUDE`:

```sql-static
CREATE INDEX orders_customer_cover_idx ON orders (customer_id) INCLUDE (amount, created_at);
```

## Как переписывать медленные запросы

### Коррелированный подзапрос → JOIN с агрегатом

Подзапрос в `SELECT` выполняется для каждой строки:

```sql-plan
EXPLAIN
SELECT p.name,
       (SELECT COUNT(*) FROM reviews AS r WHERE r.product_id = p.product_id) AS reviews_cnt
FROM products AS p;
```

В плане видно `SubPlan` — он повторяется 500 раз, по разу на товар. Посчитать отзывы один раз и присоединить итог обычно намного дешевле:

```sql-plan
EXPLAIN
SELECT p.name, COALESCE(r.cnt, 0) AS reviews_cnt
FROM products AS p
LEFT JOIN (
  SELECT product_id, COUNT(*) AS cnt
  FROM reviews
  GROUP BY product_id
) AS r ON r.product_id = p.product_id;
```

Сравни итоговые стоимости двух планов.

### Другие приёмы

- **Фильтруй как можно раньше.** Условия по одной таблице — в `WHERE`, а не в `HAVING`; фильтруй таблицу до тяжёлого соединения.
- **Не выбирай лишнего.** `SELECT *` тащит все колонки и мешает Index Only Scan.
- **`EXISTS` вместо `COUNT(*) > 0`.** EXISTS останавливается на первой найденной строке.
- **`UNION ALL` вместо `UNION`**, если повторов быть не может, — без лишней сортировки.
- **Агрегируй до JOIN**, а не после: меньше строк — дешевле соединение и нет размножения (уровень 4).
- **Обновляй статистику.** После массовой загрузки — `ANALYZE таблица`.

> **На собеседовании.** «Запрос тормозит, что делать?» Хороший ответ — алгоритм: посмотреть план (`EXPLAIN ANALYZE`), найти самый дорогой узел, проверить расхождение оценок и факта, проверить, используются ли индексы и sargable ли условия, и только потом — создать индекс или переписать запрос.

## Признаки для модели: срез во времени

Аналитики часто готовят данные для моделей машинного обучения прямо в SQL: одна строка — один объект (клиент), колонки — **признаки** (features), отдельная колонка — **целевая переменная** (target), то, что модель учится предсказывать.

Пример задачи: предсказать отток — сделает ли клиент заказ в ближайшие 30 дней. Для этого выбирают **дату среза** (cutoff) и строго соблюдают правило:

- **признаки** считаются только по данным **до** среза;
- **целевая переменная** — только по данным **после** среза.

```sql
WITH params AS (
  SELECT '2026-06-01'::timestamp AS cutoff
),
features AS (
  SELECT o.customer_id,
         COUNT(*) AS orders_before,
         SUM(o.amount) AS revenue_before,
         EXTRACT(DAY FROM p.cutoff - MAX(o.created_at)) AS days_since_last
  FROM orders AS o
  CROSS JOIN params AS p
  WHERE o.created_at < p.cutoff
  GROUP BY o.customer_id, p.cutoff
),
target AS (
  SELECT DISTINCT o.customer_id
  FROM orders AS o
  CROSS JOIN params AS p
  WHERE o.created_at >= p.cutoff
    AND o.created_at <  p.cutoff + interval '30 days'
)
SELECT f.customer_id,
       f.orders_before,
       f.revenue_before,
       f.days_since_last,
       (t.customer_id IS NOT NULL)::int AS bought_next_30d
FROM features AS f
LEFT JOIN target AS t ON t.customer_id = f.customer_id
ORDER BY f.customer_id
LIMIT 8;
```

Классический набор признаков поведения клиента — **RFM**: Recency (давность последней покупки), Frequency (частота), Monetary (сумма). К ним добавляют средний чек, долю отмен, разнообразие категорий, активность за последние 7/30/90 дней.

### Утечка данных

**Утечка** (data leakage) — когда в признаки попадает информация, недоступная в момент прогноза. Модель находит «подсказку из будущего», показывает отличное качество на исторических данных и проваливается в бою.

Типичные источники утечки в SQL:

- признак посчитан по **всей** истории, без условия `< cutoff` — например, общее число заказов клиента включает заказы после среза;
- использована колонка, которая заполняется **после** события: статус «доставлен», дата вручения, итоговая оценка;
- нормировка или средние посчитаны по всей выборке, включая тестовую часть;
- дубли одного клиента попали и в обучение, и в тест.

> **Ловушка.** Если модель «слишком хороша» — точность 99% на задаче, где эксперты угадывают в 70% случаев, — первым делом ищи утечку. Почти всегда она есть.

## Разбиение на train и test

Модель обучают на одной части объектов (train), а качество проверяют на другой (test). Разбиение должно быть:

- **случайным** — без систематического перекоса;
- **воспроизводимым** — при повторном запуске клиент попадает в ту же часть;
- **по объекту** — все строки одного клиента в одной части.

`random()` не воспроизводим. Хеш от идентификатора — да:

```sql
SELECT CASE WHEN abs(hashtext(customer_id::text)) % 10 < 8 THEN 'train' ELSE 'test' END AS split,
       COUNT(*) AS customers
FROM customers
GROUP BY 1
ORDER BY 1;
```

`hashtext` всегда даёт одно и то же число для одной строки, а остаток от деления на 10 распределён примерно равномерно, — поэтому около 80% клиентов уходит в train.

Для временных задач (прогноз будущего) часто разбивают **по времени**: обучаются на срезах до некоторой даты, проверяются на более поздних. Это честнее имитирует реальное использование модели.

## pgvector: поиск похожих

**Эмбеддинг** — вектор чисел, который описывает объект так, что похожие объекты получают близкие векторы. Эмбеддинги товаров, текстов, картинок строят нейросети. Расширение **pgvector** добавляет в PostgreSQL тип `vector` и операторы расстояния.

В ShopData у каждого товара есть вектор из 8 чисел:

```sql
SELECT p.name, e.embedding
FROM product_embeddings AS e
JOIN products AS p ON p.product_id = e.product_id
ORDER BY p.product_id
LIMIT 3;
```

| Оператор | Расстояние | Смысл |
| --- | --- | --- |
| `<->` | евклидово (L2) | длина отрезка между точками |
| `<=>` | косинусное | 1 − косинус угла между векторами: учитывает направление, а не длину |
| `<#>` | отрицательное скалярное произведение | для нормированных векторов эквивалентно косинусному |

Пять товаров, ближайших к товару 1:

```sql
SELECT p.product_id,
       p.name,
       ROUND((e.embedding <=> target.embedding)::numeric, 4) AS cos_distance
FROM product_embeddings AS e
JOIN products AS p ON p.product_id = e.product_id
CROSS JOIN (SELECT embedding FROM product_embeddings WHERE product_id = 1) AS target
WHERE e.product_id <> 1
ORDER BY e.embedding <=> target.embedding
LIMIT 5;
```

Ключевые детали:

- **исключи сам объект** (`product_id <> 1`), иначе он окажется первым с расстоянием 0;
- сортировка по расстоянию + `LIMIT` — это и есть поиск k ближайших соседей (kNN);
- к векторному поиску можно добавлять обычные условия: только активные товары, только другая категория, цена в диапазоне.

### Индексы для векторов

Точный поиск сравнивает запрос со всеми векторами — на 500 товарах это мгновенно, на 10 миллионах — нет. Для больших таблиц строят **приближённые** индексы:

```sql-static
CREATE INDEX ON product_embeddings USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON product_embeddings USING ivfflat (embedding vector_l2_ops) WITH (lists = 100);
```

- **HNSW** — многоуровневый граф соседей: быстрый и точный, но долго строится и занимает больше памяти;
- **IVFFlat** — делит векторы на кластеры и ищет в ближайших: строится быстро, точность зависит от числа просматриваемых кластеров.

Класс операторов индекса (`vector_cosine_ops`, `vector_l2_ops`) должен совпадать с оператором в запросе: индекс по косинусу не ускорит поиск по `<->`. На маленькой таблице планировщик честно выберет полный перебор — индекс ему не нужен.

## Типичные ошибки

### Функция над индексированной колонкой

`WHERE created_at::date = …`, `EXTRACT(…)`, `col::text = …` выключают индекс. Перепиши в диапазон или создай индекс по выражению.

### Индекс «на всё»

Каждый индекс замедляет запись. Создавай индексы под реальные запросы и проверяй, что план их использует.

### Составной индекс не в том порядке

Индекс `(created_at, customer_id)` плохо помогает поиску по одному клиенту. Первой ставь колонку равенства.

### Признаки без среза

Агрегат по всей истории в признаке — утечка. В каждом CTE с признаками должно быть условие `< cutoff`.

### Случайное разбиение через random()

Каждый запуск даёт другой train и test. Используй хеш от ключа объекта.

### Объект среди своих соседей

В kNN-запросе не забудь исключить сам объект.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Посмотреть план | `EXPLAIN SELECT …` |
| План с реальным временем | `EXPLAIN ANALYZE SELECT …` |
| Индекс по колонке | `CREATE INDEX name ON t (col)` |
| Индекс по выражению | `CREATE INDEX name ON t (lower(email))` |
| Составной индекс | `CREATE INDEX name ON t (a, b)` — равенство первым |
| Частичный индекс | `CREATE INDEX name ON t (col) WHERE cond` |
| Покрывающий индекс | `CREATE INDEX name ON t (a) INCLUDE (b, c)` |
| День без потери индекса | `ts >= 'день' AND ts < 'следующий день'` |
| Обновить статистику | `ANALYZE t` |
| Признаки до среза | `WHERE created_at < cutoff` в каждом расчёте признаков |
| Таргет после среза | `WHERE created_at >= cutoff AND created_at < cutoff + interval '30 days'` |
| Воспроизводимый split | `abs(hashtext(id::text)) % 10 < 8` |
| Ближайшие по косинусу | `ORDER BY embedding <=> target LIMIT k` |

## Проверь себя

?? Почему `WHERE EXTRACT(YEAR FROM created_at) = 2025` не использует индекс по created_at, а диапазон дат — использует?
:: В индексе хранятся значения created_at, отсортированные по времени. Результат EXTRACT в индексе не хранится, поэтому базе приходится вычислять его для каждой строки. Диапазон по самой колонке позволяет найти начало в индексе и пройти до конца диапазона.

?? В плане `Seq Scan`. Это всегда плохо?
:: Нет. Если нужна большая часть строк или таблица маленькая, последовательное чтение дешевле индекса. Плохо, когда Seq Scan читает огромную таблицу ради нескольких строк.

?? Индекс создан по `(customer_id, created_at)`. Поможет ли он запросу `WHERE created_at >= '2026-06-01'`?
:: Почти нет: индекс отсортирован сначала по customer_id, и условие только по второй колонке не позволяет найти нужный участок. Правило левого префикса.

?? Модель оттока показывает 99% точности на исторических данных. Что проверить первым?
:: Утечку: не попали ли в признаки данные после даты среза (агрегаты по всей истории, статусы и даты, известные только постфактум).

?? Зачем в kNN-запросе условие `e.product_id <> 1`?
:: Иначе ближайшим «похожим» окажется сам товар с расстоянием 0.

?? Чем `random() < 0.8` хуже `abs(hashtext(id::text)) % 10 < 8` для разбиения train/test?
:: random() каждый раз даёт новое разбиение — эксперименты нельзя повторить, а клиент может «переехать» между выборками. Хеш от ключа детерминирован.
