На этом уровне почти нет новых ключевых слов — зато есть **приёмы**. Медиана, подытоги, воронка, когорты, retention, серии подряд, A/B-тест — задачи, которые продуктовый и data-аналитик решает каждую неделю и которые чаще всего спрашивают на собеседованиях. Каждый приём собран из уже знакомых деталей: CTE, окон, условной агрегации. Здесь мы разберём их как рецепты: что считается, почему именно так и где обычно ошибаются.

## Медиана и перцентили

Среднее чувствительно к выбросам. Один заказ на миллион поднимает средний чек всего магазина. Медиана — значение «посередине» упорядоченного ряда — устойчива к выбросам и лучше описывает «типичный» заказ.

```sql
SELECT ROUND(AVG(amount)) AS avg_check,
       ROUND((percentile_cont(0.5) WITHIN GROUP (ORDER BY amount))::numeric) AS median_check,
       ROUND((percentile_cont(0.9) WITHIN GROUP (ORDER BY amount))::numeric) AS p90_check
FROM orders;
```

Средний чек почти в три раза больше медианного — распределение сильно скошено вправо: много небольших заказов и немного очень крупных. Отчёт «средний чек» без медианы в такой ситуации вводит в заблуждение.

### Синтаксис упорядоченных агрегатов

`percentile_cont(p) WITHIN GROUP (ORDER BY x)` — агрегатная функция особого вида: ей нужен порядок значений, и он задаётся в `WITHIN GROUP`. Работает с `GROUP BY` как обычный агрегат:

```sql
SELECT delivery_city,
       COUNT(*) AS orders_cnt,
       ROUND(percentile_cont(0.5) WITHIN GROUP (ORDER BY amount)::numeric) AS median_check
FROM orders
GROUP BY delivery_city
ORDER BY median_check DESC
LIMIT 5;
```

| Функция | Что возвращает |
| --- | --- |
| `percentile_cont(p)` | интерполирует между соседними значениями, тип double precision |
| `percentile_disc(p)` | первое реальное значение, у которого доля ≥ p, тип исходной колонки |
| `mode()` | самое частое значение |
| `percentile_cont(ARRAY[0.25, 0.5, 0.75])` | сразу несколько квантилей массивом |

> **Важно.** `percentile_cont` возвращает `double precision`, а `round(x, 2)` для этого типа не определён. Приводи к numeric: `round(percentile_cont(0.5) WITHIN GROUP (ORDER BY amount)::numeric, 2)`.

> **Ловушка.** Функции `median()` в PostgreSQL нет. Запрос с ней упадёт с ошибкой `function median(numeric) does not exist`. На собеседованиях это любят проверять.

## Подытоги: ROLLUP, CUBE, GROUPING SETS

Отчёт «выручка по кварталам с итогами по годам и общим итогом» можно собрать из трёх запросов через `UNION ALL`. Но `GROUP BY` умеет это сам.

```sql
SELECT EXTRACT(YEAR FROM created_at) AS y,
       EXTRACT(QUARTER FROM created_at) AS q,
       SUM(amount) AS revenue
FROM orders
WHERE created_at >= '2025-01-01'
GROUP BY ROLLUP (EXTRACT(YEAR FROM created_at), EXTRACT(QUARTER FROM created_at))
ORDER BY y, q;
```

`ROLLUP (a, b)` — это группировки `(a, b)`, `(a)` и `()`: детальные строки, подытог по каждому `a` и общий итог. В подытогах «свёрнутые» колонки равны NULL.

| Конструкция | Какие наборы группировки |
| --- | --- |
| `ROLLUP (a, b)` | `(a, b)`, `(a)`, `()` — иерархия «детали → подытог → итог» |
| `CUBE (a, b)` | `(a, b)`, `(a)`, `(b)`, `()` — все комбинации |
| `GROUPING SETS ((a), (b))` | только перечисленные: итоги по `a` и отдельно по `b` |

`GROUPING SETS` удобен, когда в одной таблице нужны два независимых среза — например, заказы по статусам и по городам доставки:

```sql
SELECT status,
       delivery_city,
       COUNT(*) AS orders_cnt
FROM orders
GROUP BY GROUPING SETS ((status), (delivery_city))
ORDER BY status NULLS LAST, orders_cnt DESC;
```

В строках первого среза пуст город, в строках второго — статус. Это то же самое, что два запроса с `GROUP BY status` и `GROUP BY delivery_city`, склеенные через `UNION ALL`, но за один проход по таблице.

### GROUPING() отличает подытог от NULL в данных

Если в самой колонке бывают NULL, строка подытога неотличима от группы «NULL». Функция `GROUPING(col)` возвращает 1, если колонка свёрнута в этой строке, и 0 — если это настоящее значение.

```sql
SELECT CASE WHEN GROUPING(department) = 1 THEN 'ВСЕГО' ELSE department END AS department,
       COUNT(*) AS people,
       SUM(salary) AS payroll
FROM employees
GROUP BY ROLLUP (department)
ORDER BY GROUPING(department), department;
```

## Сводная таблица: строки в колонки

Pivot — разложить значения одной колонки по нескольким колонкам. В PostgreSQL для этого обычно хватает условной агрегации:

```sql
SELECT delivery_city,
       COUNT(*) FILTER (WHERE created_at >= '2026-04-01' AND created_at < '2026-05-01') AS apr,
       COUNT(*) FILTER (WHERE created_at >= '2026-05-01' AND created_at < '2026-06-01') AS may,
       COUNT(*) FILTER (WHERE created_at >= '2026-06-01' AND created_at < '2026-07-01') AS jun
FROM orders
GROUP BY delivery_city
ORDER BY jun DESC
LIMIT 6;
```

Колонки приходится перечислять вручную — SQL не умеет создавать колонки «по данным». Для динамического pivot есть расширение `tablefunc` с функцией `crosstab`, но чаще такие таблицы разворачивают уже в BI-инструменте или pandas.

## Воронка

Воронка показывает, сколько пользователей дошло до каждого шага: просмотр → корзина → оформление → покупка — и какая доля «отвалилась» на каждом переходе.

В ShopData события лежат в `events`: одна строка — одно действие внутри сессии.

```sql
SELECT session_id,
       string_agg(event_type, ' → ' ORDER BY event_ts) AS path
FROM events
GROUP BY session_id
ORDER BY session_id
LIMIT 5;
```

Воронка по сессиям — число сессий, где был каждый шаг:

```sql
WITH steps AS (
  SELECT COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'view')        AS viewed,
         COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'add_to_cart') AS carted,
         COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'checkout')    AS checkout,
         COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'purchase')    AS purchased
  FROM events
)
SELECT viewed,
       carted,
       ROUND(100.0 * carted / viewed, 1) AS view_to_cart_pct,
       checkout,
       ROUND(100.0 * checkout / carted, 1) AS cart_to_checkout_pct,
       purchased,
       ROUND(100.0 * purchased / checkout, 1) AS checkout_to_purchase_pct,
       ROUND(100.0 * purchased / viewed, 1) AS total_cr_pct
FROM steps;
```

Ключевые решения в воронке:

- **единица счёта** — сессия, пользователь или день. Здесь сессия: `COUNT(DISTINCT session_id)`. Если считать события, два просмотра в одной сессии дадут лишний «вход» в воронку;
- **шаговая или общая конверсия**: шаг к предыдущему шагу показывает, где теряем, конверсия к первому шагу — общую эффективность;
- **порядок шагов**: строгая воронка требует, чтобы шаги шли по порядку во времени. Простая версия выше считает «был ли шаг в сессии».

Воронку в виде строк (шаг, сессии, конверсия к предыдущему) удобно строить через `LAG`:

```sql
WITH counts AS (
  SELECT event_type, COUNT(DISTINCT session_id) AS sessions
  FROM events
  GROUP BY event_type
),
ordered AS (
  SELECT event_type,
         sessions,
         CASE event_type WHEN 'view' THEN 1 WHEN 'add_to_cart' THEN 2
                         WHEN 'checkout' THEN 3 ELSE 4 END AS step
  FROM counts
)
SELECT step,
       event_type,
       sessions,
       ROUND(100.0 * sessions / LAG(sessions) OVER (ORDER BY step), 1) AS from_prev_pct
FROM ordered
ORDER BY step;
```

## JSONB: данные без схемы

У событий есть колонка `props` типа `jsonb` — гибкий набор атрибутов: устройство, товар. Основные операторы:

| Оператор | Что делает | Пример |
| --- | --- | --- |
| `->` | значение по ключу как JSON | `props -> 'device'` → `"mobile"` |
| `->>` | значение по ключу как текст | `props ->> 'device'` → `mobile` |
| `#>>` | значение по пути как текст | `props #>> '{a,b}'` |
| `?` | есть ли ключ | `props ? 'product_id'` |
| `@>` | содержит ли пары | `props @> '{"device": "mobile"}'` |

```sql
SELECT props ->> 'device' AS device,
       COUNT(DISTINCT session_id) AS sessions,
       COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'purchase') AS purchased,
       ROUND(100.0 * COUNT(DISTINCT session_id) FILTER (WHERE event_type = 'purchase')
             / COUNT(DISTINCT session_id), 1) AS cr_pct
FROM events
GROUP BY props ->> 'device'
ORDER BY cr_pct DESC;
```

Число из JSON нужно привести: `(props ->> 'product_id')::int` — тогда его можно соединить с `products`.

## Когорты

**Когорта** — группа пользователей, объединённых общим событием в одном периоде. Чаще всего — месяцем первой покупки. Когортный анализ отвечает на вопрос: «Как ведут себя клиенты, пришедшие в разные месяцы?» — и не смешивает новичков со старожилами.

Шаг 1 — когорта каждого клиента:

```sql
WITH first_orders AS (
  SELECT customer_id,
         date_trunc('month', MIN(created_at))::date AS cohort_month
  FROM orders
  GROUP BY customer_id
)
SELECT cohort_month, COUNT(*) AS cohort_size
FROM first_orders
WHERE cohort_month >= '2026-01-01'
GROUP BY cohort_month
ORDER BY cohort_month;
```

Шаг 2 — для каждого заказа посчитать, через сколько месяцев после прихода клиента он сделан. Номер месяца удобно получить формулой `год × 12 + месяц`: разность таких чисел — это разница в месяцах.

```sql-static
(EXTRACT(YEAR FROM o.created_at) * 12 + EXTRACT(MONTH FROM o.created_at))
- (EXTRACT(YEAR FROM f.cohort_month) * 12 + EXTRACT(MONTH FROM f.cohort_month)) AS month_n
```

`month_n = 0` — месяц первой покупки, `1` — следующий и так далее.

## Retention

**Retention месяца k** — доля когорты, которая сделала заказ через k месяцев после первого. Это главный показатель «возвращаемости».

```sql
WITH first_orders AS (
  SELECT customer_id,
         date_trunc('month', MIN(created_at))::date AS cohort_month
  FROM orders
  GROUP BY customer_id
),
activity AS (
  SELECT DISTINCT
         f.customer_id,
         f.cohort_month,
         (EXTRACT(YEAR FROM o.created_at) * 12 + EXTRACT(MONTH FROM o.created_at))
       - (EXTRACT(YEAR FROM f.cohort_month) * 12 + EXTRACT(MONTH FROM f.cohort_month)) AS month_n
  FROM first_orders AS f
  JOIN orders AS o ON o.customer_id = f.customer_id
),
sizes AS (
  SELECT cohort_month, COUNT(*) AS cohort_size
  FROM first_orders
  GROUP BY cohort_month
)
SELECT a.cohort_month,
       s.cohort_size,
       CASE WHEN a.cohort_month + interval '1 month' <= '2026-06-01'
            THEN ROUND(100.0 * COUNT(*) FILTER (WHERE a.month_n = 1) / s.cohort_size, 1) END AS m1_pct,
       CASE WHEN a.cohort_month + interval '2 months' <= '2026-06-01'
            THEN ROUND(100.0 * COUNT(*) FILTER (WHERE a.month_n = 2) / s.cohort_size, 1) END AS m2_pct,
       CASE WHEN a.cohort_month + interval '3 months' <= '2026-06-01'
            THEN ROUND(100.0 * COUNT(*) FILTER (WHERE a.month_n = 3) / s.cohort_size, 1) END AS m3_pct
FROM activity AS a
JOIN sizes AS s ON s.cohort_month = a.cohort_month
WHERE a.cohort_month >= '2025-10-01'
GROUP BY a.cohort_month, s.cohort_size
ORDER BY a.cohort_month;
```

Детали, на которых ошибаются:

- `DISTINCT` в `activity`: клиент с тремя заказами в одном месяце должен считаться **один** раз;
- знаменатель — **размер когорты**, а не число активных в месяце 0;
- у свежих когорт последних месяцев ещё не наступили — их ячейки нужно оставлять пустыми, а не нулевыми. Когорта мая 2026 не может иметь retention третьего месяца: он ещё не прошёл. Поэтому каждая колонка в запросе обёрнута в `CASE`: если месяц `k` для когорты ещё не наступил (данные заканчиваются июнем 2026), вместо 0 будет NULL.

> **На собеседовании.** «Посчитай retention по когортам» — один из самых частых тестовых вопросов для продуктового аналитика. Проговаривай вслух определения: что такое когорта, что считается «активностью», какой знаменатель.

## Серии подряд: gaps and islands

Задача: найти непрерывные серии — дни подряд с заказами у клиента, месяцы подряд с ростом, периоды без сбоев. Это называют «острова и пропуски».

Ключевой трюк: для значений, идущих подряд, **разность между значением и его порядковым номером постоянна**.

| день | номер строки | день − номер |
| --- | --- | --- |
| 10 июня | 1 | 9 июня |
| 11 июня | 2 | 9 июня |
| 12 июня | 3 | 9 июня |
| 15 июня | 4 | 11 июня |
| 16 июня | 5 | 11 июня |

Строки с одинаковой разностью — один остров. Дальше группируем по ней.

```sql
WITH days AS (
  SELECT DISTINCT customer_id, created_at::date AS order_date
  FROM orders
),
marked AS (
  SELECT customer_id,
         order_date,
         order_date - ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date)::int AS grp
  FROM days
)
SELECT customer_id,
       MIN(order_date) AS streak_start,
       MAX(order_date) AS streak_end,
       COUNT(*) AS days_in_row
FROM marked
GROUP BY customer_id, grp
HAVING COUNT(*) >= 2
ORDER BY days_in_row DESC, customer_id
LIMIT 5;
```

`DISTINCT` на первом шаге обязателен: два заказа в один день иначе разорвут серию — у них разные номера строк, но одна дата.

Другой способ — через `LAG`: отметить строку флагом «начало новой серии», если разрыв с предыдущей больше 1, и посчитать нарастающую сумму флагов — она и будет номером острова. Этот вариант гибче: разрыв можно определить как угодно (больше 7 дней, другой статус…).

## A/B-тест

В `ab_assignments` клиенты распределены по группам A и B эксперимента `new_checkout`. Нужно сравнить конверсию в покупку между группами.

```sql
WITH users AS (
  SELECT customer_id, variant, assigned_at
  FROM ab_assignments
  WHERE experiment = 'new_checkout'
),
converted AS (
  SELECT u.customer_id
  FROM users AS u
  WHERE EXISTS (
    SELECT 1 FROM events AS e
    WHERE e.customer_id = u.customer_id
      AND e.event_type = 'purchase'
      AND e.event_ts >= u.assigned_at
  )
)
SELECT u.variant,
       COUNT(*) AS users,
       COUNT(c.customer_id) AS buyers,
       ROUND(100.0 * COUNT(c.customer_id) / COUNT(*), 2) AS cr_pct
FROM users AS u
LEFT JOIN converted AS c ON c.customer_id = u.customer_id
GROUP BY u.variant
ORDER BY u.variant;
```

Правила корректного A/B-анализа в SQL:

- **считать только события после распределения** (`event_ts >= assigned_at`). Покупки до эксперимента не могли быть вызваны новым оформлением, но если их учесть, они размоют разницу;
- **знаменатель — все распределённые**, а не только те, у кого были события. Пользователь, который ничего не сделал, — тоже результат;
- **единица анализа** совпадает с единицей рандомизации: распределяли клиентов — считаем клиентов, а не сессии;
- разница конверсий — ещё не вывод. Нужна проверка статистической значимости (z-тест для долей, бутстреп), и её обычно делают уже вне SQL.

> **Совет.** Перед сравнением метрик проверь сам эксперимент: примерно ли равны группы по размеру (sample ratio mismatch), нет ли клиентов в обеих группах сразу, совпадают ли периоды распределения.

## Типичные ошибки

### Среднее вместо медианы

Для денег, длительностей и количеств распределение почти всегда скошено. Показывай медиану рядом со средним.

### Функция median()

Её нет. Используй `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)`.

### Подытоги, которые нельзя отличить от NULL

В `ROLLUP` по колонке с пропусками используй `GROUPING(col)`.

### Воронка по событиям вместо сессий

`COUNT(*)` по событиям завышает шаги, где пользователь кликает много раз. Считай `COUNT(DISTINCT session_id)`.

### Retention без DISTINCT

Клиент с несколькими заказами в месяце считается несколько раз, и retention может стать больше 100%.

### Конверсия A/B с событиями до эксперимента

Без условия `event_ts >= assigned_at` конверсия считается и по «доэкспериментальному» поведению.

### Серии без DISTINCT по датам

Повторяющиеся даты ломают трюк «дата минус номер строки».

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Медиана | `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)` |
| Медиана с округлением | `round((percentile_cont(0.5) WITHIN GROUP (ORDER BY x))::numeric, 2)` |
| Самое частое значение | `mode() WITHIN GROUP (ORDER BY x)` |
| Детали + подытоги + итог | `GROUP BY ROLLUP (a, b)` |
| Два независимых среза | `GROUP BY GROUPING SETS ((a), (b))` |
| Отличить подытог | `GROUPING(a) = 1` |
| Pivot | `COUNT(*) FILTER (WHERE period = …) AS col` для каждой колонки |
| Шаг воронки | `COUNT(DISTINCT session_id) FILTER (WHERE event_type = …)` |
| Текст из JSON | `props ->> 'key'` |
| Когорта | `date_trunc('month', MIN(created_at))` по клиенту |
| Номер месяца жизни | `(год*12 + месяц) − (год_когорты*12 + месяц_когорты)` |
| Острова | `дата − ROW_NUMBER() OVER (PARTITION BY id ORDER BY дата)` как ключ группы |
| Конверсия A/B | события после `assigned_at`, знаменатель — все в группе |

## Проверь себя

?? Почему средний чек может быть в несколько раз больше медианного?
:: Распределение сумм скошено вправо: немного очень крупных заказов тянут среднее вверх, а медиана от них почти не зависит.

?? Сколько строк вернёт `GROUP BY ROLLUP (year, quarter)` для двух лет по четыре квартала?
:: 11: 8 детальных строк (год × квартал), 2 подытога по годам и 1 общий итог.

?? Почему в воронке считают `COUNT(DISTINCT session_id)`, а не `COUNT(*)`?
:: Одна сессия может содержать несколько одинаковых событий (три просмотра, две корзины). Воронка отвечает на вопрос «сколько сессий дошло до шага», а не «сколько раз нажали».

?? Retention первого месяца у когорты получился 120%. Что пошло не так?
:: Скорее всего, клиенты с несколькими заказами в месяце посчитаны несколько раз. Нужен DISTINCT по клиенту и номеру месяца перед подсчётом.

?? В чём трюк «дата минус ROW_NUMBER» для поиска серий?
:: Если даты идут подряд, и дата, и номер строки растут на 1 на каждом шаге, поэтому их разность постоянна. При разрыве дата прыгает сильнее номера, и разность меняется — начинается новый остров.

?? Почему в A/B-тесте важно условие `event_ts >= assigned_at`?
:: События до распределения не могли зависеть от варианта. Если их учесть, в конверсию обеих групп попадёт одинаковый «шум», и реальная разница уменьшится.
