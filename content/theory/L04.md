В хорошо спроектированной базе каждый факт хранится в одном месте: имя клиента — в `customers`, состав заказа — в `order_items`, название категории — в `categories`. Это удобно для хранения, но почти любой отчёт требует собрать факты вместе: «заказы с именами клиентов», «выручка по категориям», «сотрудник и его руководитель». Для этого таблицы **соединяют** — `JOIN`. Это самая важная и самая коварная тема базового SQL: соединение может незаметно потерять строки или размножить их. На этом уровне разберёмся, как этого не допустить.

## Зачем данные разложены по таблицам

Представь, что все данные о заказе лежали бы в одной большой таблице: номер заказа, имя клиента, его телефон, город, название товара, категория… Тогда при смене телефона пришлось бы обновлять все заказы клиента, а опечатка в одной строке создавала бы «двух разных» клиентов. Поэтому данные **нормализуют**: каждая сущность — в своей таблице, а связи — через ключи.

Связи в ShopData:

| Связь | Как соединять |
| --- | --- |
| заказ → клиент | `orders.customer_id = customers.customer_id` |
| позиция → заказ | `order_items.order_id = orders.order_id` |
| позиция → товар | `order_items.product_id = products.product_id` |
| товар → категория | `products.category_id = categories.category_id` |
| категория → родительская категория | `categories.parent_id = categories.category_id` |
| платёж, доставка, промокод → заказ | `… .order_id = orders.order_id` |
| отзыв → товар и клиент | `reviews.product_id`, `reviews.customer_id` |
| остаток → склад и товар | `stock.warehouse_id`, `stock.product_id` |
| сотрудник → руководитель | `employees.manager_id = employees.employee_id` |

### Кардинальность связи

Прежде чем соединять, полезно понимать, сколько строк с каждой стороны может соответствовать друг другу:

- **один к одному**: заказ и его доставка — у заказа не больше одной строки в `deliveries`;
- **один ко многим**: клиент и его заказы — у клиента может быть много заказов, у заказа ровно один клиент;
- **многие ко многим**: заказы и товары — в заказе много товаров, товар есть во многих заказах. Такая связь всегда идёт через промежуточную таблицу — здесь это `order_items`.

Кардинальность определяет, сколько строк получится после соединения. Держи её в голове — и половина ошибок этого уровня не случится.

## INNER JOIN

```sql
SELECT o.order_id,
       o.created_at,
       c.first_name,
       c.last_name,
       o.amount
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
ORDER BY o.created_at DESC
LIMIT 5;
```

- `JOIN` (полностью — `INNER JOIN`) берёт каждую строку левой таблицы и ищет в правой строки, для которых условие `ON` истинно.
- Каждая найденная пара становится строкой результата.
- Строки, не нашедшие пары, в результат **не попадают** ни с одной стороны.

### Псевдонимы таблиц

`orders AS o` даёт таблице короткое имя. После этого колонку можно уточнить: `o.order_id`, `c.first_name`. Уточнять **обязательно**, если колонка с таким именем есть в нескольких таблицах запроса — иначе база не знает, какую взять:

```sql-error
SELECT order_id, customer_id, first_name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id;
```

Ошибка `column reference "customer_id" is ambiguous`. Хорошая привычка — уточнять **все** колонки в запросах с JOIN, даже уникальные: так видно, откуда что берётся.

### USING

Если колонки связи называются одинаково, условие можно сократить:

```sql
SELECT o.order_id, d.courier, d.shipped_at
FROM orders AS o
JOIN deliveries AS d USING (order_id)
LIMIT 5;
```

`USING (order_id)` — то же, что `ON d.order_id = o.order_id`, но колонка `order_id` в результате будет одна и без префикса.

### Цепочка соединений

Соединений в запросе может быть сколько угодно. Каждый следующий JOIN присоединяет таблицу к уже собранному результату:

```sql
SELECT o.order_id,
       p.name AS product,
       cat.name AS category,
       i.quantity,
       i.price
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.order_id
JOIN products AS p ON p.product_id = i.product_id
JOIN categories AS cat ON cat.category_id = p.category_id
WHERE o.order_id = 1500;
```

> **Совет.** Пиши условие `ON` сразу после таблицы, которую присоединяешь, и сравнивай её ключ с уже присоединённой: `JOIN products AS p ON p.product_id = i.product_id`. Так цепочку легко читать сверху вниз.

## LEFT JOIN: не терять строки

INNER JOIN выбрасывает строки без пары. Иногда это ровно то, что нужно (заказы с данными о доставке), а иногда — серьёзная ошибка. «Сколько отзывов у каждого товара» через INNER JOIN покажет только товары, у которых отзывы **есть**, и товары с нулём отзывов исчезнут из отчёта.

`LEFT JOIN` сохраняет **все** строки левой таблицы. Если пары не нашлось, колонки правой таблицы заполняются NULL.

```sql
SELECT p.product_id,
       p.name,
       r.review_id,
       r.rating
FROM products AS p
LEFT JOIN reviews AS r ON r.product_id = p.product_id
ORDER BY r.review_id NULLS FIRST, p.product_id
LIMIT 6;
```

Первые строки — товары без отзывов: `review_id` и `rating` у них NULL.

### Виды внешних соединений

| Соединение | Какие строки сохраняются |
| --- | --- |
| `JOIN` / `INNER JOIN` | только пары |
| `LEFT JOIN` | все строки левой таблицы + пары |
| `RIGHT JOIN` | все строки правой таблицы + пары |
| `FULL JOIN` | все строки обеих таблиц |
| `CROSS JOIN` | все комбинации, без условия |

`RIGHT JOIN` — это `LEFT JOIN` с таблицами наоборот. На практике почти всегда пишут `LEFT`, переставляя таблицы: читать запрос, где главная таблица стоит первой, проще.

`FULL JOIN` нужен для сверок: «что есть в одной системе, но нет в другой, и наоборот».

## Anti-join: строки без пары

Вопросы вида «клиенты без заказов», «товары без продаж», «заказы без оплаты» решаются через **anti-join**: LEFT JOIN, а потом оставить только строки, где пара не нашлась.

```sql
SELECT c.customer_id, c.first_name, c.last_name, c.registered_at
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL
ORDER BY c.registered_at
LIMIT 5;
```

Проверять на NULL нужно колонку, которая **не может** быть NULL у настоящей пары, — лучше всего ключ правой таблицы (`o.order_id`). Если проверять колонку, где NULL бывает и сам по себе (например, `o.delivery_address`), в результат попадут лишние строки.

Тот же вопрос можно решить через `NOT EXISTS` — это будет на следующем уровне.

## Условие в ON или в WHERE

Для `INNER JOIN` всё равно, где стоит дополнительное условие: в `ON` или в `WHERE`. Для `LEFT JOIN` — **совсем не всё равно**.

Задача: показать всех клиентов и число их заказов за июнь 2026 (у кого не было — ноль).

```sql
SELECT c.customer_id,
       COUNT(o.order_id) AS june_orders
FROM customers AS c
LEFT JOIN orders AS o
       ON o.customer_id = c.customer_id
      AND o.created_at >= '2026-06-01'
GROUP BY c.customer_id
ORDER BY june_orders, c.customer_id
LIMIT 5;
```

Условие на дату стоит в `ON`: оно решает, **какие заказы присоединять**. Клиенты без июньских заказов остаются с нулём.

Если перенести условие в `WHERE`:

```sql
SELECT COUNT(DISTINCT c.customer_id) AS customers_in_result
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.created_at >= '2026-06-01';
```

`WHERE` выполняется **после** соединения и выбрасывает строки, где `o.created_at` равен NULL, — то есть всех клиентов без июньских заказов. LEFT JOIN фактически превратился в INNER, и нули из отчёта пропали.

> **Ловушка.** Условие на правую таблицу LEFT JOIN в `WHERE` (кроме `IS NULL` для anti-join) почти всегда ошибка. Правило: условия «какие строки присоединять» — в `ON`, условия «какие строки результата оставить» — в `WHERE`.

## COUNT после LEFT JOIN

```sql
SELECT p.product_id,
       COUNT(*) AS count_star,
       COUNT(r.review_id) AS count_reviews
FROM products AS p
LEFT JOIN reviews AS r ON r.product_id = p.product_id
GROUP BY p.product_id
ORDER BY count_reviews, p.product_id
LIMIT 5;
```

У товара без отзывов LEFT JOIN создаёт одну строку, где колонки `reviews` — NULL. `COUNT(*)` считает эту строку и выдаёт 1. `COUNT(r.review_id)` пропускает NULL и выдаёт правильный 0.

Аналогично `SUM(r.rating)` для таких товаров даст NULL — оберни в `COALESCE(SUM(…), 0)`, если нужен ноль.

## Размножение строк

Самая опасная ошибка с JOIN — **fan-out**, размножение строк. Соединение «один ко многим» повторяет строку левой таблицы для каждой пары справа. Если к одной таблице присоединить две независимые «многие», строки перемножаются.

```sql
SELECT c.customer_id,
       COUNT(*) AS joined_rows,
       COUNT(DISTINCT o.order_id) AS orders_cnt,
       COUNT(DISTINCT r.review_id) AS reviews_cnt
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.customer_id
JOIN reviews AS r ON r.customer_id = c.customer_id
GROUP BY c.customer_id
ORDER BY joined_rows DESC
LIMIT 3;
```

У клиента с 17 заказами и 7 отзывами получается 17 × 7 = 119 строк. Любой `SUM(o.amount)` в таком запросе умножит выручку клиента на 7.

Как защититься:

1. **Агрегировать до соединения.** Посчитать заказы по клиентам и отзывы по клиентам отдельно (подзапросом или CTE), а потом соединить готовые итоги — один к одному.
2. **`COUNT(DISTINCT …)`** — спасает счётчики, но не суммы: `SUM(DISTINCT amount)` склеит разные заказы с одинаковой суммой.
3. **Проверять число строк.** После каждого JOIN спроси: должно ли число строк вырасти? Если «заказы с клиентами» вернули больше строк, чем заказов, — что-то не так.

```sql
SELECT c.customer_id,
       o.orders_cnt,
       o.revenue,
       r.reviews_cnt
FROM customers AS c
JOIN (SELECT customer_id, COUNT(*) AS orders_cnt, SUM(amount) AS revenue
      FROM orders GROUP BY customer_id) AS o ON o.customer_id = c.customer_id
JOIN (SELECT customer_id, COUNT(*) AS reviews_cnt
      FROM reviews GROUP BY customer_id) AS r ON r.customer_id = c.customer_id
ORDER BY o.orders_cnt DESC
LIMIT 3;
```

Здесь каждая подтаблица уже содержит одну строку на клиента, поэтому соединение ничего не размножает. Подзапросы в `FROM` подробно разберём на следующем уровне.

> **На собеседовании.** «Почему выручка в отчёте больше, чем в бухгалтерии?» — один из любимых вопросов. Правильный ответ почти всегда — размножение строк при JOIN.

## Self-join: таблица сама с собой

Иногда связь ведёт в ту же таблицу: сотрудник → руководитель, категория → родительская категория. Тогда таблицу присоединяют саму к себе под разными псевдонимами:

```sql
SELECT e.full_name AS employee,
       e.position,
       m.full_name AS manager
FROM employees AS e
LEFT JOIN employees AS m ON m.employee_id = e.manager_id
ORDER BY e.employee_id
LIMIT 8;
```

`e` — сотрудники, `m` — те же сотрудники в роли руководителей. LEFT JOIN нужен, чтобы не потерять генерального директора: у него нет руководителя.

То же для категорий:

```sql
SELECT child.name AS category,
       parent.name AS parent_category
FROM categories AS child
JOIN categories AS parent ON parent.category_id = child.parent_id
ORDER BY parent.name, child.name;
```

Self-join видит только один уровень. Чтобы пройти дерево на любую глубину, нужна рекурсия — уровень 6.

## CROSS JOIN и соединение по неравенству

`CROSS JOIN` соединяет каждую строку с каждой — **декартово произведение**: 5 складов × 25 категорий = 125 строк.

```sql
SELECT w.name AS warehouse, c.name AS category
FROM warehouses AS w
CROSS JOIN categories AS c
WHERE c.parent_id IS NULL
ORDER BY w.warehouse_id, c.category_id
LIMIT 8;
```

Зачем это нужно? Чтобы построить «сетку» всех комбинаций (склад × категория, день × товар) и потом присоединить к ней факты через LEFT JOIN — тогда пустые клетки получат 0, а не исчезнут.

Условие соединения не обязано быть равенством. Например, промокод действовал в момент заказа:

```sql
SELECT o.order_id, o.created_at, pc.code, pc.valid_from, pc.valid_to
FROM order_promos AS op
JOIN orders AS o ON o.order_id = op.order_id
JOIN promo_codes AS pc
  ON pc.code = op.code
 AND o.created_at::date BETWEEN pc.valid_from AND pc.valid_to
LIMIT 5;
```

> **Ловушка.** Забытое условие соединения превращает JOIN в CROSS JOIN. 6 000 заказов × 2 000 клиентов — это 12 миллионов строк. Если запрос внезапно «завис» или вернул неправдоподобно много строк, проверь все `ON`.

## Типичные ошибки

### Потерянные нули

«Выручка по категориям» через INNER JOIN не покажет категории без продаж. Если в отчёте должны быть все категории — LEFT JOIN от `categories` и `COALESCE(SUM(…), 0)`.

### Условие LEFT JOIN в WHERE

`LEFT JOIN orders o … WHERE o.status = 'paid'` — это INNER JOIN. Условие на присоединяемую таблицу — в `ON`.

### COUNT(*) после LEFT JOIN

Даёт 1 вместо 0. Считай ключ правой таблицы: `COUNT(r.review_id)`.

### Размножение при двух «многих»

Заказы и отзывы, заказы и платежи (у части заказов бывает два платежа) — соединяя такие таблицы, агрегируй до JOIN.

### Неоднозначная колонка

`column reference "…" is ambiguous` — уточни таблицу: `o.customer_id`.

### Соединение не по тем ключам

`JOIN products p ON p.product_id = o.order_id` выполнится без ошибки и вернёт мусор: номера совпадают случайно. Сверяйся со схемой: соединяй внешний ключ с первичным ключом, на который он ссылается.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Только строки с парой | `FROM a JOIN b ON b.a_id = a.id` |
| Все строки слева | `FROM a LEFT JOIN b ON …` |
| Строки слева без пары | `LEFT JOIN b ON … WHERE b.id IS NULL` |
| Фильтр присоединяемых строк | условие в `ON … AND b.x = …` |
| Число пар, с нулями | `COUNT(b.id)` после LEFT JOIN |
| Сумма, с нулями | `COALESCE(SUM(b.x), 0)` |
| Одинаковые имена колонок связи | `JOIN b USING (id)` |
| Сотрудник и руководитель | `employees e LEFT JOIN employees m ON m.employee_id = e.manager_id` |
| Все комбинации | `a CROSS JOIN b` |
| Сверка двух источников | `a FULL JOIN b ON …` |
| Без размножения | агрегировать каждую «многую» таблицу до JOIN |

## Проверь себя

?? В таблице A 10 строк, в B — 3. Сколько строк даст `A CROSS JOIN B`?
:: 30 — каждая строка A с каждой строкой B.

?? Почему для «клиентов без заказов» проверяют `o.order_id IS NULL`, а не `o.delivery_address IS NULL`?
:: order_id у настоящего заказа никогда не NULL, поэтому NULL в нём означает только одно — пары нет. delivery_address бывает NULL и у существующих заказов, и такие клиенты ошибочно попадут в результат.

?? Запрос «заказы с именами клиентов» вернул больше строк, чем заказов в таблице. Что могло случиться?
:: Соединение размножило строки: например, условие соединения не по ключу, или в запрос попала ещё одна таблица «многие» (позиции, платежи). У заказа ровно один клиент, поэтому правильное соединение не может увеличить число строк.

?? Чем отличаются `LEFT JOIN orders o ON … AND o.status = 'paid'` и `LEFT JOIN orders o ON … WHERE o.status = 'paid'`?
:: Первый присоединяет только оплаченные заказы, но сохраняет всех клиентов (у кого таких нет — с NULL). Второй после соединения выбрасывает все строки, где статус не paid, включая клиентов без заказов, — то есть работает как INNER JOIN.

?? У товара 0 отзывов. Что вернут `COUNT(*)` и `COUNT(r.review_id)` после LEFT JOIN с отзывами?
:: 1 и 0. LEFT JOIN создаёт одну строку-заглушку с NULL в колонках отзыва: COUNT(*) её считает, COUNT(r.review_id) — нет.

?? Как получить список категорий второго уровня вместе с названием родителя?
:: Self-join: `FROM categories AS child JOIN categories AS parent ON parent.category_id = child.parent_id`.
