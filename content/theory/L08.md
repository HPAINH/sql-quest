На прошлом уровне окно было «группой без схлопывания». Теперь научимся смотреть **вдоль** окна: брать значение из предыдущей строки, копить сумму от начала периода, считать скользящее среднее за неделю, делить клиентов на квартили. Это инструменты анализа временных рядов — метрики «к прошлому месяцу», нарастающие итоги, сглаживание шума. Главное новое понятие уровня — **рамка окна**: именно из-за неё одна и та же функция иногда ведёт себя неожиданно.

## LAG и LEAD: соседние строки

`LAG(x)` возвращает значение `x` из **предыдущей** строки окна, `LEAD(x)` — из **следующей**. Порядок задаёт `ORDER BY` внутри `OVER`.

```sql
WITH monthly AS (
  SELECT date_trunc('month', created_at)::date AS month,
         SUM(amount) AS revenue
  FROM orders
  WHERE status = 'delivered' AND created_at >= '2025-07-01'
  GROUP BY 1
)
SELECT month,
       revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS diff,
       ROUND(100.0 * (revenue / LAG(revenue) OVER (ORDER BY month) - 1), 1) AS growth_pct
FROM monthly
ORDER BY month;
```

У первой строки предыдущей нет — `LAG` возвращает NULL, и рост для неё не считается. Это правильно: сравнивать не с чем.

### Полная форма

`LAG(x, offset, default)`:

- `offset` — на сколько строк назад смотреть (по умолчанию 1);
- `default` — что вернуть, если такой строки нет (по умолчанию NULL).

`LAG(revenue, 12)` по помесячным данным — тот же месяц год назад (если в ряду нет пропусков). `LAG(revenue, 1, 0)` — ноль вместо NULL для первой строки.

### Внутри групп

С `PARTITION BY` соседи ищутся только внутри группы. Сколько дней прошло между заказами клиента:

```sql
SELECT customer_id,
       order_id,
       created_at,
       LAG(created_at) OVER (PARTITION BY customer_id ORDER BY created_at) AS prev_order_at,
       created_at::date - LAG(created_at::date) OVER (PARTITION BY customer_id ORDER BY created_at) AS days_since_prev
FROM orders
WHERE customer_id IN (1, 2)
ORDER BY customer_id, created_at;
```

`LEAD` смотрит вперёд — например, когда клиент вернулся после текущего заказа и вернулся ли вообще:

```sql
SELECT customer_id,
       order_id,
       created_at,
       LEAD(created_at) OVER (PARTITION BY customer_id ORDER BY created_at) AS next_order_at
FROM orders
WHERE customer_id = 44
ORDER BY created_at;
```

У последнего заказа `next_order_at` — NULL: следующего пока не было.

> **Ловушка.** `LAG` берёт предыдущую **строку**, а не предыдущий **период**. Если в помесячном ряду пропущен месяц (продаж не было), `LAG` вернёт позапрошлый месяц, и «рост к прошлому месяцу» будет посчитан неверно. Для рядов с возможными пропусками сначала построй календарь (уровень 6), потом считай `LAG`.

## Нарастающий итог

Агрегат с `ORDER BY` в окне превращается в нарастающий: каждая строка получает итог от начала окна до себя.

```sql
WITH daily AS (
  SELECT created_at::date AS order_date,
         SUM(amount) AS revenue
  FROM orders
  WHERE created_at >= '2026-06-01'
  GROUP BY 1
)
SELECT order_date,
       revenue,
       SUM(revenue) OVER (ORDER BY order_date) AS revenue_to_date
FROM daily
ORDER BY order_date
LIMIT 10;
```

С `PARTITION BY` итог начинается заново в каждой группе — например, нарастающая выручка внутри каждого месяца или накопленные траты каждого клиента:

```sql
SELECT customer_id,
       created_at,
       amount,
       SUM(amount) OVER (PARTITION BY customer_id ORDER BY created_at) AS spent_to_date,
       COUNT(*)    OVER (PARTITION BY customer_id ORDER BY created_at) AS orders_to_date
FROM orders
WHERE customer_id = 44
ORDER BY created_at;
```

Почему это работает «само собой»? Ответ — в рамке окна.

## Рамка окна

Для каждой строки окно — это раздел (`PARTITION BY`), упорядоченный по `ORDER BY`. **Рамка** (frame) уточняет, какие строки раздела **вокруг текущей** участвуют в вычислении агрегата.

```sql-static
ROWS BETWEEN <начало> AND <конец>
```

Границы:

| Граница | Смысл |
| --- | --- |
| `UNBOUNDED PRECEDING` | первая строка раздела |
| `n PRECEDING` | n строк до текущей |
| `CURRENT ROW` | текущая строка |
| `n FOLLOWING` | n строк после текущей |
| `UNBOUNDED FOLLOWING` | последняя строка раздела |

Примеры:

| Рамка | Что считается |
| --- | --- |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | от начала до текущей — нарастающий итог |
| `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` | текущая и 6 предыдущих — скользящие 7 строк |
| `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` | соседи с обеих сторон — центрированное окно из 3 |
| `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` | весь раздел |

### Рамка по умолчанию

Если рамка не указана:

- **без** `ORDER BY` в окне — рамка весь раздел;
- **с** `ORDER BY` — `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, то есть от начала раздела до текущей строки **и всех строк с тем же значением ORDER BY**.

Поэтому `SUM(x) OVER (PARTITION BY g)` даёт итог группы, а `SUM(x) OVER (PARTITION BY g ORDER BY ts)` — нарастающий итог. Слово `ORDER BY` молча меняет рамку.

## ROWS, RANGE и GROUPS

Режим рамки определяет, как считать «n строк до текущей»:

- `ROWS` — по физическим строкам;
- `RANGE` — по **значению** ключа сортировки: строки с одинаковым значением («пиры», peers) всегда входят в рамку вместе. С `RANGE` можно задать и смещение по значению: `RANGE BETWEEN interval '6 days' PRECEDING AND CURRENT ROW`;
- `GROUPS` — по группам пиров: `GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW` — текущая группа одинаковых значений и предыдущая.

Разница видна на ничьих:

```sql
SELECT x,
       SUM(x) OVER (ORDER BY x) AS default_range,
       SUM(x) OVER (ORDER BY x ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS by_rows
FROM (VALUES (1), (2), (2), (3)) AS t(x);
```

Для двух строк со значением 2 режим `RANGE` (по умолчанию) включает в рамку **обе** — и обе получают итог 5. Режим `ROWS` идёт по строкам: 3, затем 5.

> **Ловушка.** Нарастающий итог по колонке с повторами (например, по дате, когда в день несколько заказов) с рамкой по умолчанию «прыгает»: все заказы одного дня получают одинаковый итог на конец дня. Если нужен итог по каждой строке, добавь тай-брейкер в `ORDER BY` (`ORDER BY created_at, order_id`) или явно укажи `ROWS`.

## Скользящее среднее

Скользящее среднее сглаживает дневной шум и показывает тренд.

```sql
WITH daily AS (
  SELECT created_at::date AS order_date,
         COUNT(*) AS orders_cnt
  FROM orders
  WHERE created_at >= '2026-06-01'
  GROUP BY 1
)
SELECT order_date,
       orders_cnt,
       ROUND(AVG(orders_cnt) OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 1) AS ma_7,
       COUNT(*) OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS days_in_window
FROM daily
ORDER BY order_date
LIMIT 10;
```

Обрати внимание на `days_in_window`: в первые шесть дней окно неполное, и «среднее за 7 дней» на самом деле считается по 1, 2, 3… дням. В отчёте такие строки часто отбрасывают или помечают.

### Неделя — это 7 строк или 7 дней?

`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` — это 7 **строк**. Если в данных есть дни без продаж, 7 строк растянутся больше чем на неделю. Два решения:

1. Построить календарь без пропусков (уровень 6), тогда строка = день.
2. Использовать `RANGE` со смещением по времени — тогда рамка считается по значению даты:

```sql
WITH daily AS (
  SELECT created_at::date AS order_date, COUNT(*) AS orders_cnt
  FROM orders
  WHERE created_at >= '2025-01-01'
  GROUP BY 1
)
SELECT order_date,
       orders_cnt,
       SUM(orders_cnt) OVER (ORDER BY order_date RANGE BETWEEN interval '6 days' PRECEDING AND CURRENT ROW) AS orders_7d
FROM daily
ORDER BY order_date
LIMIT 8;
```

> **Совет.** «Неделя» из `6 PRECEDING AND CURRENT ROW` — это 7 строк. Частая ошибка — написать `7 PRECEDING` и получить 8. Считай: текущая строка + n предыдущих = n + 1.

## FIRST_VALUE, LAST_VALUE, NTH_VALUE

Эти функции берут значение из конкретной строки рамки:

- `FIRST_VALUE(x)` — из первой строки рамки;
- `LAST_VALUE(x)` — из последней;
- `NTH_VALUE(x, n)` — из n-й.

Самый дешёвый товар категории рядом с каждым товаром:

```sql
SELECT category_id,
       name,
       price,
       FIRST_VALUE(name) OVER (PARTITION BY category_id ORDER BY price) AS cheapest_in_category
FROM products
WHERE category_id IN (9, 10)
ORDER BY category_id, price
LIMIT 8;
```

### Ловушка LAST_VALUE

С рамкой по умолчанию (`… AND CURRENT ROW`) последняя строка рамки — это **текущая строка** (или последний её пир). Поэтому `LAST_VALUE` «не работает»:

```sql
SELECT x,
       LAST_VALUE(x) OVER (ORDER BY x) AS last_default,
       LAST_VALUE(x) OVER (ORDER BY x ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_full
FROM (VALUES (1), (2), (2), (3)) AS t(x);
```

Чтобы получить настоящее последнее значение раздела, расширь рамку до конца: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`. Или используй `FIRST_VALUE` с обратной сортировкой — у него такой проблемы нет.

## Квантили и относительное положение

### NTILE

`NTILE(n)` делит упорядоченные строки на n почти равных корзин и возвращает номер корзины. Квартили клиентов по сумме покупок:

```sql
WITH spend AS (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  WHERE status = 'delivered'
  GROUP BY customer_id
)
SELECT quartile,
       COUNT(*) AS customers,
       MIN(total) AS min_total,
       MAX(total) AS max_total,
       SUM(total) AS revenue
FROM (
  SELECT customer_id, total, NTILE(4) OVER (ORDER BY total DESC) AS quartile
  FROM spend
) AS q
GROUP BY quartile
ORDER BY quartile;
```

Первая четверть клиентов обычно приносит непропорционально большую долю выручки — это видно по колонке `revenue`.

`NTILE` делит по **числу строк**, не по значениям: если строк не делится нацело, первые корзины получают на одну строку больше, а равные значения могут попасть в разные корзины.

### PERCENT_RANK и CUME_DIST

- `PERCENT_RANK()` = (ранг − 1) / (строк − 1), от 0 до 1 — какая доля строк «ниже» текущей;
- `CUME_DIST()` = (число строк ≤ текущей) / (всего строк), от 1/N до 1.

«Верхние 10% клиентов» — это `CUME_DIST() OVER (ORDER BY total DESC) <= 0.1`:

```sql
WITH spend AS (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  GROUP BY customer_id
),
ranked AS (
  SELECT customer_id, total,
         ROUND(CUME_DIST() OVER (ORDER BY total DESC)::numeric, 4) AS cume
  FROM spend
)
SELECT COUNT(*) AS top10_customers, SUM(total) AS top10_revenue
FROM ranked
WHERE cume <= 0.1;
```

## Именованные окна и комбинации

Когда в запросе много функций по одному окну, его стоит назвать:

```sql
WITH daily AS (
  SELECT created_at::date AS order_date, SUM(amount) AS revenue
  FROM orders
  WHERE created_at >= '2026-06-01'
  GROUP BY 1
)
SELECT order_date,
       revenue,
       LAG(revenue) OVER w AS prev_day,
       SUM(revenue) OVER w AS cumulative,
       ROUND(AVG(revenue) OVER (w ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)) AS ma_7
FROM daily
WINDOW w AS (ORDER BY order_date)
ORDER BY order_date
LIMIT 8;
```

`OVER (w ROWS …)` наследует от `w` порядок и добавляет свою рамку.

## Типичные ошибки

### LAST_VALUE возвращает текущую строку

Рамка по умолчанию заканчивается на текущей строке. Нужна `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

### Восьмидневная неделя

`ROWS BETWEEN 7 PRECEDING AND CURRENT ROW` — это 8 строк. Для 7 дней — `6 PRECEDING`.

### Пропуски в ряду

`LAG` и `ROWS` работают со строками. Если дни или месяцы без данных отсутствуют, «вчера» и «неделя» сдвигаются. Строй календарь или используй `RANGE` с интервалом.

### Нарастающий итог «скачет» на ничьих

С рамкой `RANGE` по умолчанию строки с одинаковым ключом получают одинаковый итог. Добавь тай-брейкер или `ROWS`.

### Рост к прошлому периоду через целое деление

`(cnt - prev_cnt) / prev_cnt` для целых счётчиков даст 0. Нужно `100.0 * (cnt - prev_cnt) / prev_cnt` и защита `NULLIF(prev_cnt, 0)`.

### Неполное окно в начале ряда

Первые строки скользящего среднего считаются по меньшему числу точек. Если это важно, отфильтруй их по `COUNT(*) OVER (… ROWS …) = 7`.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Значение прошлого периода | `LAG(x) OVER (ORDER BY period)` |
| Значение следующей строки | `LEAD(x) OVER (PARTITION BY g ORDER BY ts)` |
| Год назад в помесячном ряду | `LAG(x, 12) OVER (ORDER BY month)` |
| Рост в процентах | `100.0 * (x / NULLIF(LAG(x) OVER w, 0) - 1)` |
| Нарастающий итог | `SUM(x) OVER (ORDER BY ts)` |
| Нарастающий итог без скачков | `SUM(x) OVER (ORDER BY ts, id ROWS UNBOUNDED PRECEDING)` |
| Скользящее среднее 7 строк | `AVG(x) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` |
| Сумма за 7 календарных дней | `SUM(x) OVER (ORDER BY d RANGE BETWEEN interval '6 days' PRECEDING AND CURRENT ROW)` |
| Первое значение группы | `FIRST_VALUE(x) OVER (PARTITION BY g ORDER BY ts)` |
| Последнее значение группы | `LAST_VALUE(x) OVER (… ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)` |
| Квартиль | `NTILE(4) OVER (ORDER BY x DESC)` |
| Верхние 10% | `CUME_DIST() OVER (ORDER BY x DESC) <= 0.1` |

## Проверь себя

?? Что вернёт `LAG(x)` для первой строки окна? А `LAG(x, 1, 0)`?
:: NULL — предыдущей строки нет. С третьим аргументом — 0.

?? Почему `SUM(amount) OVER (PARTITION BY customer_id)` и `SUM(amount) OVER (PARTITION BY customer_id ORDER BY created_at)` дают разные результаты?
:: ORDER BY в окне меняет рамку по умолчанию: без него рамка — весь раздел (итог клиента), с ним — от начала раздела до текущей строки (нарастающий итог).

?? Сколько строк в рамке `ROWS BETWEEN 2 PRECEDING AND 2 FOLLOWING`?
:: Пять: две до, текущая и две после. У краёв раздела — меньше.

?? Для значений 10, 20, 20, 30 что даст `SUM(x) OVER (ORDER BY x)` во второй и третьей строках?
:: 50 в обеих: по умолчанию рамка RANGE, и обе строки со значением 20 — пиры, которые входят в рамку вместе (10 + 20 + 20).

?? Как получить для каждого заказа клиента дату его первого заказа?
:: `FIRST_VALUE(created_at) OVER (PARTITION BY customer_id ORDER BY created_at)` или `MIN(created_at) OVER (PARTITION BY customer_id)`.

?? Чем `NTILE(10)` отличается от отбора по `CUME_DIST() <= 0.1` для «топ-10% клиентов»?
:: NTILE делит строки поровну по количеству, и клиенты с одинаковой суммой могут оказаться в разных корзинах. CUME_DIST учитывает равные значения: все клиенты с одинаковой суммой получают одинаковый CUME_DIST и либо все попадают в топ, либо все нет.
