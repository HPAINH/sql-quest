До сих пор ты только читал данные. Теперь — меняешь: добавляешь склад, поднимаешь цены, удаляешь мусор, обновляешь остатки, защищаешь таблицы ограничениями. Аналитику это нужно чаще, чем кажется: подготовить витрину, почистить дубли, загрузить справочник, исправить разметку. А ошибка в изменении данных стоит дороже ошибки в отчёте: неверный `SELECT` можно перезапустить, а `UPDATE` без `WHERE` в боевой базе — нет. Поэтому на этом уровне вместе с командами разберём **транзакции** — механизм, который делает изменения безопасными.

## Как работают задания этого уровня

В тикетах ты пишешь не запрос, а **скрипт** — одну или несколько команд через точку с запятой. Игра:

1. открывает транзакцию;
2. выполняет твой скрипт;
3. запускает проверочный запрос и смотрит на состояние данных;
4. **откатывает** всё обратно.

Так база остаётся нетронутой, и задание можно решать сколько угодно раз. Все примеры ниже работают так же: кнопка «Выполнить и откатить» запускает их в транзакции, показывает результат последней команды и отменяет изменения.

Если хоть одна команда скрипта падает, откатывается весь скрипт — это свойство транзакции, о котором подробнее в конце уровня.

> **Совет.** Заканчивай скрипт проверочным `SELECT` — тогда сразу видно, что изменилось. В примерах ниже так и сделано.

## INSERT: добавить строки

### Одна или несколько строк

```sql
INSERT INTO warehouses (warehouse_id, name, city)
VALUES (100, 'Склад Дон', 'Ростов-на-Дону');

SELECT * FROM warehouses ORDER BY warehouse_id;
```

- после имени таблицы в скобках — список колонок, которые заполняешь;
- в `VALUES` — значения в том же порядке;
- колонки, которых нет в списке, получат значение по умолчанию (`DEFAULT`) или NULL.

Несколько строк — через запятую:

```sql
INSERT INTO warehouses (warehouse_id, name, city)
VALUES (101, 'Склад Юг', 'Краснодар'),
       (102, 'Склад Приволжье', 'Самара');

SELECT * FROM warehouses WHERE warehouse_id > 100;
```

> **Важно.** Всегда перечисляй колонки явно. `INSERT INTO warehouses VALUES (…)` без списка колонок зависит от порядка колонок в таблице: если его поменяют или добавят колонку, скрипт сломается или, что хуже, запишет значения не туда.

### INSERT … SELECT

Вставить результат запроса — например, завести нулевые остатки нового склада по всем товарам бренда:

```sql
INSERT INTO warehouses (warehouse_id, name, city)
VALUES (100, 'Склад Дон', 'Ростов-на-Дону');

INSERT INTO stock (warehouse_id, product_id, qty, updated_at)
SELECT 100, product_id, 0, '2026-07-01 09:00'
FROM products
WHERE brand = 'Nova' AND is_active;

SELECT COUNT(*) AS rows_added FROM stock WHERE warehouse_id = 100;
```

Колонки `SELECT` сопоставляются с колонками `INSERT` **по порядку**, а не по именам.

### RETURNING

`RETURNING` возвращает вставленные (или изменённые, или удалённые) строки — не нужно делать отдельный `SELECT`:

```sql
INSERT INTO promo_codes (code, discount_pct, valid_from, valid_to)
VALUES ('AUTUMN26', 15, '2026-09-01', '2026-09-30')
RETURNING code, discount_pct, valid_to - valid_from AS days;
```

## UPDATE: изменить строки

```sql
UPDATE products
SET price = round(price * 1.05)
WHERE brand = 'Kvant';

SELECT name, price FROM products WHERE brand = 'Kvant' ORDER BY price DESC LIMIT 5;
```

- `SET` перечисляет колонки и новые значения через запятую;
- в выражениях справа можно использовать **старые** значения колонок этой же строки;
- `WHERE` определяет, какие строки меняются.

> **Ловушка.** `UPDATE` без `WHERE` меняет **все** строки таблицы. Это самая известная катастрофа в работе с базами. Привычка: сначала напиши `SELECT … WHERE …` с тем же условием, проверь, что выбираются нужные строки, и только потом замени `SELECT` на `UPDATE`.

### Несколько колонок и CASE

```sql
UPDATE products
SET is_active = false,
    price = CASE WHEN price > 50000 THEN price ELSE round(price * 0.9) END
WHERE brand = 'Volt' AND created_at < '2025-01-01';

SELECT name, price, is_active, created_at
FROM products
WHERE brand = 'Volt'
ORDER BY created_at
LIMIT 6;
```

Все выражения в `SET` вычисляются по **исходной** строке: если в одном `SET` поменять `price` и тут же использовать `price` в другом выражении, будет взято старое значение.

### UPDATE … FROM: по данным другой таблицы

Снять с продажи все товары одной категории, зная только её название:

```sql
UPDATE products AS p
SET is_active = false
FROM categories AS c
WHERE c.category_id = p.category_id
  AND c.name = 'Парфюмерия'
RETURNING p.product_id, p.name, c.name AS category;
```

`FROM` в `UPDATE` работает как JOIN: строка таблицы обновляется, если для неё нашлась пара. Если пар несколько, PostgreSQL возьмёт любую — поэтому условие соединения должно давать одну пару на строку.

Вместо `FROM` можно использовать подзапрос в `WHERE`:

```sql
UPDATE products
SET is_active = false
WHERE product_id IN (
  SELECT p.product_id
  FROM products AS p
  WHERE NOT EXISTS (SELECT 1 FROM order_items AS i WHERE i.product_id = p.product_id)
)
RETURNING product_id, name;
```

## DELETE: удалить строки

```sql
DELETE FROM reviews
WHERE rating = 3 AND text IS NULL
RETURNING review_id, product_id;
```

Как и с `UPDATE`, `DELETE` без `WHERE` удаляет всё. `DELETE FROM t USING other WHERE …` удаляет по данным другой таблицы — аналог `UPDATE … FROM`:

```sql
DELETE FROM order_promos AS op
USING orders AS o
WHERE o.order_id = op.order_id
  AND o.status = 'cancelled';

SELECT COUNT(*) AS promos_left FROM order_promos;
```

### TRUNCATE

`TRUNCATE таблица` очищает таблицу целиком и намного быстрее `DELETE` без условия: не перебирает строки, а освобождает файлы. Но у него нет `WHERE` и `RETURNING`, а на таблицу, на которую ссылаются внешние ключи, он без `CASCADE` не сработает.

```sql-static
TRUNCATE TABLE staging_events;
```

## Upsert: вставить или обновить

Частая задача: загрузить данные, где часть строк новые, а часть уже есть. Новые — вставить, существующие — обновить. Это **upsert** — `INSERT … ON CONFLICT`.

```sql
INSERT INTO stock (warehouse_id, product_id, qty, updated_at)
VALUES (1, 1, 10, '2026-07-01 09:00'),
       (1, 4, 25, '2026-07-01 09:00')
ON CONFLICT (warehouse_id, product_id)
DO UPDATE SET qty = stock.qty + EXCLUDED.qty,
              updated_at = EXCLUDED.updated_at
RETURNING warehouse_id, product_id, qty;
```

- `ON CONFLICT (колонки)` — по какому уникальному ключу определять «уже есть». На этих колонках должен быть первичный ключ или уникальный индекс;
- `EXCLUDED` — строка, которую **пытались** вставить;
- `stock.qty` — значение, которое **уже лежит** в таблице.

Здесь поставка суммируется с остатком: если строка была — количество растёт, если не было — вставляется новая.

Если существующие строки трогать не нужно, есть короткая форма:

```sql
INSERT INTO warehouses (warehouse_id, name, city)
VALUES (1, 'Склад Центральный', 'Москва'),
       (100, 'Склад Дон', 'Ростов-на-Дону')
ON CONFLICT (warehouse_id) DO NOTHING
RETURNING warehouse_id, name;
```

`RETURNING` покажет только реально вставленную строку — склад 1 уже существовал и пропущен.

Upsert можно ограничить условием: `DO UPDATE SET … WHERE stock.updated_at < EXCLUDED.updated_at` — обновлять, только если пришли более свежие данные.

## Ограничения: защита данных

Ограничения (constraints) — правила, которые база проверяет при каждом изменении. Нарушение — ошибка, и изменение не происходит.

| Ограничение | Что гарантирует |
| --- | --- |
| `PRIMARY KEY` | значение уникально и не NULL, строку можно однозначно найти |
| `UNIQUE` | значения уникальны (NULL допускаются и не считаются равными) |
| `NOT NULL` | значение обязательно |
| `CHECK (условие)` | условие истинно для каждой строки |
| `FOREIGN KEY … REFERENCES` | значение существует в другой таблице |
| `DEFAULT` | не ограничение, а значение по умолчанию |

### Нарушение первичного ключа

```sql-error
INSERT INTO warehouses (warehouse_id, name, city)
VALUES (1, 'Дубль', 'Москва');
```

### CHECK

В `reviews` оценка должна быть от 1 до 5, но сейчас база это не проверяет. Добавим ограничение:

```sql
ALTER TABLE reviews
  ADD CONSTRAINT reviews_rating_range CHECK (rating BETWEEN 1 AND 5);

SELECT conname, pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conname = 'reviews_rating_range';
```

После этого попытка записать оценку 6 упадёт:

```sql-error
ALTER TABLE reviews
  ADD CONSTRAINT reviews_rating_range CHECK (rating BETWEEN 1 AND 5);

UPDATE reviews SET rating = 6 WHERE review_id = 1;
```

Если в таблице уже есть строки, нарушающие условие, `ADD CONSTRAINT` не выполнится — сначала нужно почистить данные. Для больших таблиц есть вариант `ADD CONSTRAINT … NOT VALID`: правило проверяется только для новых изменений, а старые строки можно проверить позже командой `VALIDATE CONSTRAINT`.

### Внешние ключи и порядок удаления

Внешний ключ не даёт создать «висящую» ссылку и не даёт удалить строку, на которую ссылаются:

```sql-error
DELETE FROM customers WHERE customer_id = 1;
```

У клиента есть заказы, отзывы, события — удалить его нельзя, пока они существуют. Удалять нужно **снизу вверх**: сначала зависимые строки, потом главную. Поведение внешнего ключа можно задать при его создании:

| Правило | При удалении родителя |
| --- | --- |
| `ON DELETE NO ACTION` / `RESTRICT` | ошибка (по умолчанию) |
| `ON DELETE CASCADE` | удалить зависимые строки |
| `ON DELETE SET NULL` | обнулить ссылку |
| `ON DELETE SET DEFAULT` | поставить значение по умолчанию |

`CASCADE` удобен, но опасен: одно удаление может незаметно стереть тысячи строк в других таблицах.

### Уникальность по выражению

Уникальный индекс может быть по выражению — например, запретить две почты, отличающиеся только регистром:

```sql-static
CREATE UNIQUE INDEX customers_email_lower_uq ON customers (lower(email));
```

В ShopData такой индекс создать не получится: в данных уже есть дубли почт. Сначала их нужно склеить — это задача босса этого уровня.

## Создание и изменение таблиц

```sql
CREATE TABLE price_history (
  product_id  int NOT NULL REFERENCES products (product_id),
  old_price   numeric(10, 2) NOT NULL,
  new_price   numeric(10, 2) NOT NULL CHECK (new_price > 0),
  changed_at  timestamp NOT NULL DEFAULT '2026-07-01 00:00',
  PRIMARY KEY (product_id, changed_at)
);

INSERT INTO price_history (product_id, old_price, new_price)
SELECT product_id, price, round(price * 1.1)
FROM products
WHERE brand = 'Atlas';

SELECT * FROM price_history ORDER BY product_id LIMIT 5;
```

Изменение структуры — `ALTER TABLE`:

```sql-static
ALTER TABLE products ADD COLUMN weight_kg numeric(6, 2);
ALTER TABLE products ALTER COLUMN weight_kg SET DEFAULT 0;
ALTER TABLE products RENAME COLUMN weight_kg TO weight;
ALTER TABLE products DROP COLUMN weight;
```

Типы, которые встречаются чаще всего: `int` / `bigint`, `numeric(p, s)` для денег, `text`, `boolean`, `date`, `timestamp`, `jsonb`. Для автоинкремента ключа — `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.

> **Важно.** Деньги храни в `numeric`, а не в `real` или `double precision`. Числа с плавающей точкой не умеют точно представить 0.1, и копейки начинают «плыть» при суммировании.

## Изменение JSONB

```sql
UPDATE events
SET props = props || '{"promo": true}'
WHERE session_id = 1;

SELECT event_id, event_type, props FROM events WHERE session_id = 1;
```

| Операция | Как |
| --- | --- |
| Добавить или заменить ключ | `props \|\| '{"promo": true}'` |
| Удалить ключ | `props - 'promo'` |
| Задать значение по пути | `jsonb_set(props, '{promo}', 'true')` |
| Удалить по пути | `props #- '{a,b}'` |

## Изменения в CTE

В PostgreSQL `INSERT`, `UPDATE` и `DELETE` с `RETURNING` можно использовать внутри `WITH` — и передавать изменённые строки дальше. Например, одной командой снять промокоды с отменённых заказов и сохранить эти заказы в архивную таблицу:

```sql
CREATE TABLE orders_archive (LIKE orders);

WITH moved AS (
  DELETE FROM order_promos
  WHERE order_id IN (SELECT order_id FROM orders WHERE status = 'cancelled')
  RETURNING order_id
)
INSERT INTO orders_archive
SELECT o.*
FROM orders AS o
WHERE o.order_id IN (SELECT order_id FROM moved);

SELECT COUNT(*) AS archived FROM orders_archive;
```

Все части такой команды видят данные на момент её начала и выполняются как одно целое.

## Транзакции

**Транзакция** — группа команд, которая выполняется как одна: либо все изменения применяются, либо ни одного. Классический пример — перевод денег: списать с одного счёта и зачислить на другой. Если после списания что-то сломалось, деньги не должны исчезнуть.

```sql-static
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;      -- зафиксировать оба изменения
-- или ROLLBACK; — отменить оба
```

### ACID

| Свойство | Смысл |
| --- | --- |
| **A**tomicity — атомарность | всё или ничего |
| **C**onsistency — согласованность | после транзакции все ограничения соблюдены |
| **I**solation — изоляция | параллельные транзакции не видят незафиксированные изменения друг друга |
| **D**urability — долговечность | после COMMIT данные не пропадут даже при сбое |

В PostgreSQL каждая команда вне явного `BEGIN` — это отдельная транзакция. Именно поэтому одиночный `UPDATE` нельзя «отменить» после выполнения: он уже зафиксирован.

### Точки сохранения

Внутри транзакции можно поставить точку сохранения и откатиться только до неё:

```sql-static
BEGIN;
INSERT INTO warehouses VALUES (100, 'Склад Дон', 'Ростов-на-Дону');
SAVEPOINT before_stock;
INSERT INTO stock … ;          -- что-то пошло не так
ROLLBACK TO before_stock;      -- склад остаётся, остатки отменены
COMMIT;
```

### Уровни изоляции

Когда несколько транзакций работают одновременно, возможны аномалии: одна видит частичные изменения другой, повторное чтение даёт другой результат, появляются «фантомные» строки. Уровни изоляции определяют, какие из них допустимы:

| Уровень | Что гарантирует |
| --- | --- |
| `READ COMMITTED` (по умолчанию в PostgreSQL) | каждая команда видит только зафиксированные данные на момент её начала |
| `REPEATABLE READ` | вся транзакция видит один снимок данных |
| `SERIALIZABLE` | результат как при последовательном выполнении; конфликтующие транзакции падают с ошибкой и повторяются |

Аналитические отчёты из нескольких запросов удобно запускать в `REPEATABLE READ`: все запросы увидят данные на один момент, и итоги сойдутся.

> **На собеседовании.** Спрашивают ACID, разницу между `DELETE` и `TRUNCATE`, что будет при `UPDATE` без `WHERE` и как этого избежать. Хороший ответ на последний вопрос — транзакция: `BEGIN`, `UPDATE`, проверочный `SELECT`, и только потом `COMMIT`.

## Безопасная работа с изменениями

1. **Сначала SELECT.** Напиши запрос с тем же `WHERE` и посмотри, какие строки затронешь и сколько их.
2. **Транзакция.** `BEGIN`, изменение, проверка, `COMMIT` или `ROLLBACK`.
3. **RETURNING.** Видно, что именно изменилось.
4. **Счётчик строк.** PostgreSQL сообщает, сколько строк затронуто (`UPDATE 42`). Если ждал 5, а получил 5000 — `ROLLBACK`.
5. **Бэкап перед массовыми изменениями.** `CREATE TABLE products_backup AS SELECT * FROM products;` — дёшево и спасает.

## Типичные ошибки

### UPDATE или DELETE без WHERE

Меняется вся таблица. Проверяй условие через `SELECT` до изменения.

### INSERT без списка колонок

Значения попадают в колонки по порядку, который может измениться. Перечисляй колонки.

### ON CONFLICT без уникального ключа

`there is no unique or exclusion constraint matching the ON CONFLICT specification` — колонки в `ON CONFLICT (…)` должны совпадать с первичным ключом или уникальным индексом.

### Удаление сверху вниз

`violates foreign key constraint` — на удаляемую строку кто-то ссылается. Удаляй сначала зависимые строки.

### UPDATE … FROM с несколькими парами

Если одной строке соответствует несколько строк в `FROM`, обновление возьмёт произвольную. Агрегируй данные до соединения или уточни условие.

### BEGIN и COMMIT в тикетах

В игре транзакцией управляет она сама, поэтому эти команды в скрипте запрещены.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Вставить строки | `INSERT INTO t (a, b) VALUES (1, 'x'), (2, 'y')` |
| Вставить результат запроса | `INSERT INTO t (a, b) SELECT … FROM …` |
| Обновить | `UPDATE t SET a = …, b = … WHERE …` |
| Обновить по другой таблице | `UPDATE t SET … FROM s WHERE s.id = t.id AND …` |
| Удалить | `DELETE FROM t WHERE …` |
| Удалить по другой таблице | `DELETE FROM t USING s WHERE s.id = t.id AND …` |
| Увидеть изменённое | `… RETURNING *` |
| Вставить или обновить | `INSERT … ON CONFLICT (key) DO UPDATE SET x = EXCLUDED.x` |
| Вставить, если нет | `INSERT … ON CONFLICT (key) DO NOTHING` |
| Добавить проверку | `ALTER TABLE t ADD CONSTRAINT name CHECK (…)` |
| Добавить колонку | `ALTER TABLE t ADD COLUMN c type` |
| Добавить ключ в JSONB | `UPDATE t SET props = props \|\| '{"k": 1}'` |
| Всё или ничего | `BEGIN; …; COMMIT;` / `ROLLBACK;` |

## Проверь себя

?? Что сделает `UPDATE products SET price = price * 1.1` без WHERE?
:: Поднимет цену всех товаров на 10%. Именно поэтому условие проверяют заранее через SELECT, а массовые изменения делают в транзакции.

?? Чем `EXCLUDED.qty` отличается от `stock.qty` в `ON CONFLICT DO UPDATE`?
:: EXCLUDED.qty — значение из строки, которую пытались вставить. stock.qty — значение, которое уже хранится в таблице.

?? Почему нельзя удалить клиента, у которого есть заказы?
:: На него ссылается внешний ключ из orders. По умолчанию база запрещает удаление, чтобы не появились заказы без клиента. Нужно сначала удалить или переназначить зависимые строки, либо внешний ключ должен быть объявлен с ON DELETE CASCADE.

?? Скрипт из трёх команд упал на второй. Что будет с изменениями первой?
:: Внутри транзакции — откатятся вместе со всей транзакцией. Атомарность: всё или ничего.

?? В чём разница между DELETE без WHERE и TRUNCATE?
:: Результат одинаковый — пустая таблица. DELETE удаляет строки по одной (можно добавить WHERE и RETURNING, срабатывают триггеры), TRUNCATE мгновенно очищает таблицу целиком и не перебирает строки.

?? Как добавить CHECK к таблице, где уже есть нарушающие строки, не исправляя их сразу?
:: `ALTER TABLE … ADD CONSTRAINT … CHECK (…) NOT VALID` — ограничение будет проверяться для новых изменений. Старые строки можно исправить позже и выполнить `VALIDATE CONSTRAINT`.
