К этому уровню запросы стали длинными: подзапрос внутри подзапроса внутри JOIN. Читать такое тяжело, а отлаживать — ещё тяжелее. **CTE** (Common Table Expression, обобщённое табличное выражение) решает эту проблему: каждый промежуточный шаг получает имя и объявляется наверху запроса, а основной запрос читается как последний шаг цепочки. Кроме того, CTE бывают **рекурсивными** — они умеют обходить деревья и генерировать последовательности. На этом уровне ты научишься раскладывать сложные отчёты на шаги, строить календари без пропусков и ходить по иерархиям любой глубины.

## WITH: именованные шаги

CTE объявляется словом `WITH` перед основным запросом:

```sql
WITH delivered AS (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  WHERE status = 'delivered'
  GROUP BY customer_id
)
SELECT c.city,
       COUNT(*) AS buyers,
       ROUND(AVG(d.total)) AS avg_total
FROM delivered AS d
JOIN customers AS c ON c.customer_id = d.customer_id
GROUP BY c.city
ORDER BY avg_total DESC
LIMIT 5;
```

`delivered` — имя временной таблицы. Внутри основного запроса её можно использовать как обычную таблицу: в `FROM`, в `JOIN`, в подзапросах. Существует она только во время выполнения этого запроса.

Сравни с тем же запросом через подзапрос в `FROM` на прошлом уровне: логика одинаковая, но в CTE шаги идут **сверху вниз**, в порядке рассуждения, а не изнутри наружу.

## Несколько CTE

CTE перечисляются через запятую, слово `WITH` пишется один раз. Каждый следующий шаг может использовать все предыдущие.

```sql
WITH monthly AS (
  SELECT date_trunc('month', created_at)::date AS month,
         SUM(amount) AS revenue
  FROM orders
  WHERE status = 'delivered'
    AND created_at >= '2025-07-01'
  GROUP BY 1
),
stats AS (
  SELECT AVG(revenue) AS avg_revenue,
         MAX(revenue) AS best
  FROM monthly
)
SELECT m.month,
       m.revenue,
       ROUND(100.0 * m.revenue / s.avg_revenue, 1) AS pct_of_avg,
       m.revenue = s.best AS is_best
FROM monthly AS m
CROSS JOIN stats AS s
ORDER BY m.month;
```

Здесь три шага:

1. `monthly` — выручка по месяцам за последний год.
2. `stats` — средняя и лучшая выручка по этим месяцам (одна строка).
3. Основной запрос — каждый месяц рядом со статистикой. `CROSS JOIN` с одной строкой просто «приклеивает» её к каждому месяцу.

> **Совет.** Называй CTE так, чтобы основной запрос читался как текст: `delivered`, `monthly`, `first_orders`, `active_buyers`. Имена `t1`, `t2`, `tmp` превращают CTE в такой же лабиринт, как вложенные подзапросы.

### Один CTE — много раз

CTE можно использовать в запросе несколько раз. Например, сравнить каждый месяц с предыдущим, соединив `monthly` саму с собой:

```sql
WITH monthly AS (
  SELECT date_trunc('month', created_at)::date AS month,
         COUNT(*) AS orders_cnt
  FROM orders
  WHERE created_at >= '2026-01-01'
  GROUP BY 1
)
SELECT cur.month,
       cur.orders_cnt,
       prev.orders_cnt AS prev_cnt,
       cur.orders_cnt - prev.orders_cnt AS diff
FROM monthly AS cur
LEFT JOIN monthly AS prev ON prev.month = cur.month - interval '1 month'
ORDER BY cur.month;
```

На уровне 8 ту же задачу решит одна оконная функция `LAG`, но приём «соединить CTE саму с собой» полезно знать.

## Как писать запрос шагами

CTE — это ещё и способ думать. Сложную задачу удобно решать так:

1. Сформулируй, что должно быть в одной строке результата.
2. Выпиши, какие промежуточные таблицы для этого нужны.
3. Напиши первый CTE и **проверь его отдельно**: `WITH a AS (…) SELECT * FROM a LIMIT 20`.
4. Добавь следующий шаг, снова проверь. И так до конца.

Пример: доля каждого способа оплаты в выручке июня.

```sql
WITH june_payments AS (
  SELECT method, amount
  FROM payments
  WHERE paid_at >= '2026-06-01' AND paid_at < '2026-07-01'
),
by_method AS (
  SELECT method, SUM(amount) AS total
  FROM june_payments
  GROUP BY method
),
grand AS (
  SELECT SUM(total) AS all_total FROM by_method
)
SELECT b.method,
       b.total,
       ROUND(100.0 * b.total / g.all_total, 1) AS share_pct
FROM by_method AS b
CROSS JOIN grand AS g
ORDER BY share_pct DESC;
```

Каждый шаг можно проверить, заменив основной запрос на `SELECT * FROM имя_шага`. Это сильно ускоряет отладку.

## Материализация

Как PostgreSQL выполняет CTE? Начиная с версии 12 планировщик сам решает: если CTE используется **один раз**, он обычно «встраивается» в запрос как подзапрос, и оптимизатор может протолкнуть внутрь фильтры. Если CTE используется **несколько раз**, его результат обычно вычисляется один раз и сохраняется (**материализуется**).

Поведение можно задать явно:

```sql-static
WITH big AS MATERIALIZED (…)       -- посчитать один раз и сохранить
WITH big AS NOT MATERIALIZED (…)   -- встроить в каждое место использования
```

В тикетах это не понадобится, но если CTE с тяжёлым расчётом используется несколько раз и запрос тормозит — `MATERIALIZED` бывает полезен.

## Рекурсивные CTE

Обычный SQL не умеет «повторять до тех пор, пока…». Рекурсивный CTE умеет. Он состоит из двух частей, соединённых `UNION ALL`:

```sql
WITH RECURSIVE numbers AS (
  SELECT 1 AS n              -- стартовая часть
  UNION ALL
  SELECT n * 2               -- рекурсивная часть
  FROM numbers
  WHERE n < 100              -- условие остановки
)
SELECT n FROM numbers;
```

Как это выполняется:

1. Выполняется **стартовая часть** (anchor) — получаем строку `1`. Она становится «рабочим набором».
2. Выполняется **рекурсивная часть**, где `numbers` означает **только строки, найденные на предыдущем шаге**. Из `1` получаем `2`.
3. Новые строки добавляются в результат и становятся новым рабочим набором. Из `2` получаем `4`, из `4` — `8`…
4. Когда рекурсивная часть не вернула ни одной строки (из `128` ничего не получается: `128 < 100` ложно), рекурсия останавливается.

Обрати внимание: в результате есть 128 — условие `WHERE n < 100` проверяется для **предыдущей** строки (64), а не для новой.

> **Ловушка.** Рекурсия без условия остановки бесконечна. PostgreSQL будет генерировать строки, пока не кончится память или не сработает таймаут — в игре это 5 секунд. Проверяй, что рекурсивная часть рано или поздно перестаёт находить строки.

## Обход дерева сверху вниз

Категории ShopData образуют дерево: у корневых `parent_id IS NULL`, у остальных `parent_id` указывает на родителя. Self-join (уровень 4) видел только один уровень. Рекурсия проходит все.

```sql
WITH RECURSIVE tree AS (
  SELECT category_id,
         name,
         parent_id,
         0 AS depth,
         name::text AS path
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  SELECT c.category_id,
         c.name,
         c.parent_id,
         t.depth + 1,
         t.path || ' > ' || c.name
  FROM categories AS c
  JOIN tree AS t ON c.parent_id = t.category_id
)
SELECT depth, path
FROM tree
ORDER BY path;
```

- Стартовая часть — корни дерева, глубина 0.
- Рекурсивная часть ищет детей уже найденных категорий: `c.parent_id = t.category_id`.
- `depth` растёт на 1 с каждым уровнем.
- `path` копит «хлебные крошки» — путь от корня.

Сортировка по `path` выводит дерево в естественном порядке: родитель, затем его дети.

> **Важно.** Типы колонок стартовой и рекурсивной частей должны совпадать. Конкатенация `t.path || ' > ' || c.name` даёт тип `text`, поэтому в стартовой части `name` приведён к `text` явно: `name::text`. Без этого PostgreSQL может пожаловаться на несовпадение типов.

### Поддерево узла

Чтобы получить все подкатегории одной категории (на любую глубину), начни рекурсию не с корней, а с нужного узла:

```sql
WITH RECURSIVE sub AS (
  SELECT category_id, name FROM categories WHERE name = 'Электроника'
  UNION ALL
  SELECT c.category_id, c.name
  FROM categories AS c
  JOIN sub AS s ON c.parent_id = s.category_id
)
SELECT * FROM sub;
```

Дальше результат можно соединить с товарами и заказами — так считается «выручка по ветке каталога».

## Обход снизу вверх

Можно идти и в обратную сторону — от узла к корню. Цепочка руководителей сотрудника:

```sql
WITH RECURSIVE chain AS (
  SELECT employee_id, full_name, position, manager_id, 0 AS steps_up
  FROM employees
  WHERE employee_id = 40

  UNION ALL

  SELECT e.employee_id, e.full_name, e.position, e.manager_id, ch.steps_up + 1
  FROM employees AS e
  JOIN chain AS ch ON e.employee_id = ch.manager_id
)
SELECT steps_up, full_name, position
FROM chain
ORDER BY steps_up;
```

Разница с обходом вниз — только в условии соединения: вниз — `e.manager_id = ch.employee_id` (ищем подчинённых), вверх — `e.employee_id = ch.manager_id` (ищем руководителя). Рекурсия останавливается на генеральном директоре: у него `manager_id` NULL, и следующая строка не находится.

### Вся команда руководителя

```sql
WITH RECURSIVE team AS (
  SELECT employee_id, full_name, department, 0 AS level
  FROM employees
  WHERE employee_id = 5
  UNION ALL
  SELECT e.employee_id, e.full_name, e.department, t.level + 1
  FROM employees AS e
  JOIN team AS t ON e.manager_id = t.employee_id
)
SELECT level, COUNT(*) AS people
FROM team
GROUP BY level
ORDER BY level;
```

## Циклы и защита от них

В реальных данных иерархия может содержать цикл: A подчиняется B, B подчиняется A. Тогда рекурсия никогда не закончится. Защититься можно, запоминая пройденный путь в массиве и не заходя в уже посещённые узлы:

```sql
WITH RECURSIVE walk AS (
  SELECT employee_id, manager_id, ARRAY[employee_id] AS visited
  FROM employees
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.employee_id, e.manager_id, w.visited || e.employee_id
  FROM employees AS e
  JOIN walk AS w ON e.manager_id = w.employee_id
  WHERE e.employee_id <> ALL (w.visited)
)
SELECT employee_id, array_length(visited, 1) - 1 AS depth
FROM walk
ORDER BY depth DESC, employee_id
LIMIT 5;
```

`e.employee_id <> ALL (w.visited)` — «этого сотрудника ещё нет в пути». В PostgreSQL 14+ есть и встроенная конструкция `CYCLE employee_id SET is_cycle USING path`.

Простая страховка на любой случай — ограничение глубины: `WHERE t.depth < 20` в рекурсивной части.

## Календарь без пропусков

Отчёт «число отмен по дням» через `GROUP BY` не покажет дни, когда отмен не было: нет строк — нет группы. Для графиков и сравнений это плохо — день с нулём должен быть в таблице.

Решение: сначала построить **календарь** — все дни периода, — а потом присоединить к нему факты через LEFT JOIN.

`generate_series` генерирует последовательность:

```sql
SELECT d::date AS day
FROM generate_series('2026-06-01'::date, '2026-06-10'::date, interval '1 day') AS d;
```

Календарь + факты:

```sql
WITH days AS (
  SELECT d::date AS day
  FROM generate_series('2026-06-01'::date, '2026-06-14'::date, interval '1 day') AS d
),
cancels AS (
  SELECT created_at::date AS day, COUNT(*) AS cnt
  FROM orders
  WHERE status = 'cancelled'
    AND created_at >= '2026-06-01' AND created_at < '2026-06-15'
  GROUP BY 1
)
SELECT d.day,
       COALESCE(c.cnt, 0) AS cancelled
FROM days AS d
LEFT JOIN cancels AS c ON c.day = d.day
ORDER BY d.day;
```

Каждый день периода есть в результате; где отмен не было — 0.

`generate_series` работает и с числами (`generate_series(1, 10)`), и с месяцами (`interval '1 month'`). То же самое можно сделать рекурсивным CTE, но `generate_series` короче и быстрее.

> **Совет.** «Сетка × факты» — универсальный приём. Месяцы × категории, дни × склады, часы × дни недели: строишь все комбинации через `CROSS JOIN` календаря со справочником, а потом LEFT JOIN с агрегатами. Пустые клетки получают 0 вместо того, чтобы исчезнуть.

## Типичные ошибки

### Точка с запятой перед основным запросом

```sql-error
WITH t AS (SELECT 1 AS x);
SELECT * FROM t;
```

CTE — часть одного запроса. `;` после скобки завершает команду, и `WITH` без основного запроса — синтаксическая ошибка.

### Лишнее слово WITH

`WITH a AS (…), WITH b AS (…)` — ошибка. `WITH` пишется один раз, дальше — запятые.

### Рекурсия через UNION вместо UNION ALL

`UNION` тоже работает, но на каждом шаге убирает дубли — это медленнее, а в деревьях дублей обычно нет. Пиши `UNION ALL`, если нет особой причины.

### Неправильное направление соединения

Обход вниз: `child.parent_id = tree.id`. Перепутаешь — получишь обход вверх или пустой результат. Спроси себя: «ищу детей найденного узла или его родителя?»

### Несовпадение типов в рекурсии

`recursive query "tree" column 5 has type character varying in non-recursive term but type text overall` — приведи колонку стартовой части к тому же типу, что получается в рекурсивной: `name::text`.

### Потерянные дни

Отчёт по дням без календаря пропускает пустые дни. Если в задаче сказано «каждый день» — нужен `generate_series` и LEFT JOIN.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Именованный шаг | `WITH a AS (SELECT …) SELECT … FROM a` |
| Несколько шагов | `WITH a AS (…), b AS (… FROM a …) SELECT …` |
| Проверить шаг | `WITH a AS (…) SELECT * FROM a LIMIT 20` |
| Число от 1 до N | `generate_series(1, N)` |
| Все дни периода | `generate_series(start::date, end::date, interval '1 day')` |
| Дни с нулями | календарь `LEFT JOIN` факты, `COALESCE(cnt, 0)` |
| Дерево сверху вниз | `WITH RECURSIVE t AS (корни UNION ALL дети JOIN t ON child.parent_id = t.id)` |
| Цепочка вверх | рекурсия с `JOIN t ON e.id = t.parent_id` |
| Глубина узла | `0 AS depth` в старте, `t.depth + 1` в рекурсии |
| Путь от корня | `name::text AS path` и `t.path \|\| ' > ' \|\| c.name` |
| Защита от цикла | массив пройденных узлов и `id <> ALL (visited)` или ограничение глубины |

## Проверь себя

?? Сколько строк вернёт `WITH RECURSIVE n AS (SELECT 1 AS x UNION ALL SELECT x + 1 FROM n WHERE x < 5) SELECT * FROM n`?
:: Пять: 1, 2, 3, 4, 5. Из строки 5 рекурсивная часть ничего не возвращает, потому что `5 < 5` ложно.

?? Чем CTE лучше подзапроса в FROM?
:: Шаги читаются сверху вниз в порядке рассуждения, у каждого есть имя, один шаг можно использовать несколько раз и легко проверить отдельно. По производительности в современных версиях PostgreSQL разницы обычно нет.

?? Почему отчёт «заказы по дням» через GROUP BY может пропустить дни?
:: Группы создаются только из существующих строк. Если в какой-то день заказов не было, строки для него нет. Нужна сетка дат из generate_series и LEFT JOIN.

?? В рекурсивной части `numbers` — это все найденные строки или только последние?
:: Только строки, найденные на предыдущем шаге. Поэтому каждый шаг работает с «новым фронтом», а результат накапливается отдельно.

?? Как ограничить рекурсию по дереву тремя уровнями?
:: Добавить в рекурсивную часть условие на глубину: `WHERE t.depth < 2` (если корень имеет глубину 0, то уровни 0, 1, 2 — это три уровня).

?? Что нужно поменять в обходе «вниз от руководителя», чтобы пойти «вверх от сотрудника»?
:: Условие соединения: вместо `e.manager_id = t.employee_id` написать `e.employee_id = t.manager_id`, и стартовать с сотрудника, а не с руководителя.
