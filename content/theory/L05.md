Многие вопросы требуют двух шагов: сначала что-то посчитать, а потом использовать результат. «Товары дороже средней цены» — сначала средняя цена, потом сравнение. «Клиенты, которые ни разу не оставили отзыв» — сначала, кто оставлял, потом все остальные. SQL позволяет вложить один запрос в другой — это **подзапрос**. А операции над множествами (`UNION`, `INTERSECT`, `EXCEPT`) складывают и вычитают целые выборки. На этом уровне ты освоишь оба инструмента и научишься выбирать между подзапросом и JOIN.

## Что такое подзапрос

Подзапрос — это обычный `SELECT` в круглых скобках внутри другого запроса. Сначала (по смыслу) вычисляется внутренний запрос, затем его результат используется внешним.

```sql
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price
LIMIT 5;
```

Подзапрос можно выполнить отдельно — это хороший способ отладки:

```sql
SELECT AVG(price) FROM products;
```

Подзапросы различают по форме результата:

| Вид | Возвращает | Где используется |
| --- | --- | --- |
| Скалярный | одно значение (1 строка × 1 колонка) | везде, где ждут значение: `SELECT`, `WHERE`, `HAVING` |
| Список | одну колонку, много строк | `IN`, `NOT IN`, `ANY`, `ALL` |
| Табличный | таблицу | `FROM` и `JOIN` |
| Коррелированный | любое из перечисленного, но для каждой строки внешнего запроса | `WHERE`, `SELECT`, `EXISTS` |

## Скалярный подзапрос

Скалярный подзапрос должен вернуть **ровно одну строку и одну колонку**. Его можно использовать как обычное значение:

```sql
SELECT name,
       price,
       ROUND(price - (SELECT AVG(price) FROM products)) AS diff_from_avg
FROM products
ORDER BY diff_from_avg DESC
LIMIT 5;
```

Если подзапрос вернёт несколько строк, запрос упадёт:

```sql-error
SELECT name
FROM products
WHERE price = (SELECT price FROM products WHERE brand = 'Nova');
```

Ошибка `more than one row returned by a subquery used as an expression`. Если подзапрос не вернёт ни одной строки, его значение — NULL (и сравнение с ним ничего не найдёт).

Скалярные подзапросы удобны и в `HAVING` — например, бренды, у которых средняя цена выше средней по каталогу:

```sql
SELECT brand, ROUND(AVG(price)) AS avg_price
FROM products
GROUP BY brand
HAVING AVG(price) > (SELECT AVG(price) FROM products)
ORDER BY avg_price DESC
LIMIT 5;
```

## IN: подзапрос-список

`x IN (SELECT …)` — истинно, если x совпадает хотя бы с одним значением подзапроса.

```sql
SELECT customer_id, first_name, last_name
FROM customers
WHERE customer_id IN (
  SELECT customer_id
  FROM orders
  WHERE delivery_city = 'Казань' AND amount > 200000
)
ORDER BY customer_id;
```

Подзапрос возвращает список клиентов с крупными заказами в Казань, а внешний запрос показывает их данные. Повторы внутри подзапроса не важны: каждый клиент появится один раз. Это преимущество перед JOIN — тот размножил бы клиента по числу подходящих заказов.

## Ловушка NOT IN и NULL

`NOT IN` выглядит как простое отрицание `IN`, но с NULL ведёт себя неожиданно. Задача: найти сотрудников, у которых нет подчинённых, — то есть тех, чей `employee_id` не встречается в колонке `manager_id`.

```sql
SELECT COUNT(*) AS without_reports
FROM employees
WHERE employee_id NOT IN (SELECT manager_id FROM employees);
```

Результат — 0, хотя рядовых сотрудников много. Почему? У генерального директора `manager_id` равен NULL, и в списке подзапроса есть NULL. Условие `5 NOT IN (1, 2, NULL)` раскрывается в `5 <> 1 AND 5 <> 2 AND 5 <> NULL`. Последнее сравнение — NULL, и всё выражение становится NULL, а не TRUE. Ни одна строка не проходит фильтр.

Два способа исправить:

```sql
SELECT COUNT(*) AS without_reports
FROM employees
WHERE employee_id NOT IN (SELECT manager_id FROM employees WHERE manager_id IS NOT NULL);
```

```sql
SELECT COUNT(*) AS without_reports
FROM employees AS e
WHERE NOT EXISTS (
  SELECT 1 FROM employees AS s WHERE s.manager_id = e.employee_id
);
```

> **Ловушка.** Один NULL в подзапросе превращает `NOT IN` в пустой результат. Для «строк без пары» используй `NOT EXISTS` — он не чувствителен к NULL. Если всё же пишешь `NOT IN`, добавь в подзапрос `WHERE колонка IS NOT NULL`.

## Коррелированный подзапрос

Обычный подзапрос не зависит от внешнего и вычисляется один раз. **Коррелированный** ссылается на колонки внешнего запроса — и логически выполняется заново для каждой его строки.

Самый дорогой товар в каждой категории:

```sql
SELECT p.category_id, p.name, p.price
FROM products AS p
WHERE p.price = (
  SELECT MAX(x.price)
  FROM products AS x
  WHERE x.category_id = p.category_id
)
ORDER BY p.category_id;
```

Для каждой строки `p` подзапрос находит максимальную цену **в её категории** (`x.category_id = p.category_id`) и сравнивает. Псевдонимы `p` и `x` обязательны: таблица одна, и надо различать «внешнюю» и «внутреннюю» строку.

Коррелированный подзапрос в `SELECT` добавляет к каждой строке вычисленное значение:

```sql
SELECT p.name,
       p.price,
       (SELECT COUNT(*) FROM reviews AS r WHERE r.product_id = p.product_id) AS reviews_cnt
FROM products AS p
ORDER BY reviews_cnt DESC
LIMIT 5;
```

> **Совет.** Коррелированные подзапросы наглядны, но на больших таблицах могут быть медленными: подзапрос выполняется для каждой строки. Тот же результат обычно даёт JOIN с заранее агрегированной таблицей — на уровне 11 сравним их планы.

## EXISTS и NOT EXISTS

`EXISTS (подзапрос)` — истинно, если подзапрос вернул **хотя бы одну строку**. Что именно он выбирает, неважно, поэтому принято писать `SELECT 1`.

Клиенты, оставившие хотя бы один отзыв с оценкой 1:

```sql
SELECT c.customer_id, c.first_name, c.last_name
FROM customers AS c
WHERE EXISTS (
  SELECT 1
  FROM reviews AS r
  WHERE r.customer_id = c.customer_id
    AND r.rating = 1
)
ORDER BY c.customer_id
LIMIT 5;
```

Товары, которые ни разу не покупали:

```sql
SELECT p.product_id, p.name, p.is_active
FROM products AS p
WHERE NOT EXISTS (
  SELECT 1 FROM order_items AS i WHERE i.product_id = p.product_id
)
ORDER BY p.product_id
LIMIT 5;
```

Почему `EXISTS` так любят:

- он не размножает строки: клиент с десятью подходящими отзывами появится один раз;
- `NOT EXISTS` корректно работает с NULL;
- база может остановить поиск на первой найденной строке.

### EXISTS, IN или JOIN?

| Задача | Удобнее всего |
| --- | --- |
| Есть ли пара (semi-join) | `EXISTS` или `IN` |
| Нет пары (anti-join) | `NOT EXISTS` или `LEFT JOIN … IS NULL` |
| Нужны колонки из второй таблицы | `JOIN` |
| Нужна статистика по второй таблице | `JOIN` с агрегированным подзапросом |

PostgreSQL обычно строит для `EXISTS`, `IN` и соответствующего JOIN одинаково эффективные планы, так что выбирай то, что точнее выражает смысл.

## Подзапрос в FROM

Подзапрос в `FROM` — это временная таблица, которая существует только во время выполнения запроса. У неё обязательно должен быть псевдоним.

Средняя выручка на клиента по городам — сначала суммы по клиентам, потом среднее по городу:

```sql
SELECT c.city,
       COUNT(*) AS buyers,
       ROUND(AVG(t.total)) AS avg_revenue_per_buyer
FROM (
  SELECT customer_id, SUM(amount) AS total
  FROM orders
  WHERE status = 'delivered'
  GROUP BY customer_id
) AS t
JOIN customers AS c ON c.customer_id = t.customer_id
GROUP BY c.city
ORDER BY avg_revenue_per_buyer DESC
LIMIT 5;
```

Это и есть «агрегат от агрегата»: в SQL нельзя написать `AVG(SUM(amount))` в одном запросе, но можно сначала посчитать суммы в подзапросе, а потом усреднить их снаружи.

Подзапрос в `FROM` также позволяет обойти ограничение на псевдонимы: внутри посчитать колонку, снаружи по ней фильтровать.

```sql
SELECT *
FROM (
  SELECT name, price, cost, price - cost AS margin
  FROM products
) AS t
WHERE margin > 70000
ORDER BY margin DESC;
```

Когда подзапросов становится несколько и они вложены друг в друга, запрос трудно читать. На следующем уровне появятся CTE — тот же подзапрос, но с именем и наверху запроса.

### LATERAL: подзапрос, который видит соседей

Обычный подзапрос в `FROM` не может ссылаться на другие таблицы того же `FROM`. С ключевым словом `LATERAL` — может, и тогда он выполняется для каждой строки левой части. Классический пример — последний заказ каждого клиента:

```sql
SELECT c.customer_id, c.first_name, last_order.order_id, last_order.created_at
FROM customers AS c
CROSS JOIN LATERAL (
  SELECT o.order_id, o.created_at
  FROM orders AS o
  WHERE o.customer_id = c.customer_id
  ORDER BY o.created_at DESC
  LIMIT 1
) AS last_order
ORDER BY c.customer_id
LIMIT 5;
```

`CROSS JOIN LATERAL` отбрасывает клиентов без заказов; чтобы их сохранить, пишут `LEFT JOIN LATERAL (…) AS t ON true`. На уровне 7 ту же задачу решим оконной функцией.

## ANY и ALL

`ANY` и `ALL` сравнивают значение со всеми элементами списка:

- `x > ANY (подзапрос)` — x больше хотя бы одного значения (то есть больше минимума);
- `x > ALL (подзапрос)` — x больше каждого значения (то есть больше максимума);
- `x = ANY (подзапрос)` — то же, что `IN`;
- `x <> ALL (подзапрос)` — то же, что `NOT IN` (с той же ловушкой NULL).

Товары дороже любого товара бренда Echo:

```sql
SELECT name, brand, price
FROM products
WHERE price > ALL (SELECT price FROM products WHERE brand = 'Echo')
ORDER BY price
LIMIT 5;
```

То же самое можно записать как `price > (SELECT MAX(price) …)`. Вариант с `MAX` проще читается, но `ALL` иногда встречается на собеседованиях.

> **Ловушка.** Если подзапрос для `ALL` вернул **пустой** список, `x > ALL (…)` истинно для любого x — «больше каждого из нуля значений». А `x > (SELECT MAX …)` в этом случае сравнит с NULL и ничего не вернёт.

## Операции над множествами

Если подзапросы вкладывают запросы друг в друга, то `UNION`, `INTERSECT` и `EXCEPT` ставят их **рядом** и комбинируют результаты как множества строк.

| Операция | Результат |
| --- | --- |
| `A UNION B` | строки из A или из B, без повторов |
| `A UNION ALL B` | все строки A и все строки B, с повторами |
| `A INTERSECT B` | строки, которые есть и в A, и в B |
| `A EXCEPT B` | строки A, которых нет в B |

Правила:

- у запросов одинаковое число колонок и совместимые типы;
- имена колонок берутся из первого запроса;
- `ORDER BY` и `LIMIT` пишутся один раз в самом конце и относятся ко всему результату.

Все города, где у нас есть клиенты или склады:

```sql
SELECT city FROM customers
UNION
SELECT city FROM warehouses
ORDER BY city;
```

Города с клиентами, где нет склада:

```sql
SELECT city FROM customers
EXCEPT
SELECT city FROM warehouses
ORDER BY city;
```

Города, где есть и клиенты, и склад:

```sql
SELECT city FROM customers
INTERSECT
SELECT city FROM warehouses
ORDER BY city;
```

### UNION или UNION ALL

`UNION` убирает повторы — для этого базе нужно отсортировать или захешировать весь результат. `UNION ALL` просто склеивает, это быстрее. Сравни:

```sql
SELECT
  (SELECT COUNT(*) FROM (SELECT city FROM customers UNION SELECT city FROM warehouses) AS u) AS union_rows,
  (SELECT COUNT(*) FROM (SELECT city FROM customers UNION ALL SELECT city FROM warehouses) AS ua) AS union_all_rows;
```

Правило: если повторов быть не может или они нужны — `UNION ALL`. `UNION` — только когда повторы надо убрать.

### Склейка разных источников

`UNION ALL` часто используют, чтобы собрать «ленту» из разных таблиц. Добавь колонку-метку, чтобы понимать, откуда строка:

```sql
SELECT 'заказ' AS kind, order_id AS id, created_at AS ts
FROM orders WHERE customer_id = 44
UNION ALL
SELECT 'отзыв', review_id, created_at
FROM reviews WHERE customer_id = 44
ORDER BY ts DESC
LIMIT 8;
```

> **Важно.** `INTERSECT` и `EXCEPT` сравнивают **строки целиком** и считают NULL равными друг другу — в отличие от `=` и `IN`. Это делает `EXCEPT` удобным для сверки двух таблиц: `SELECT * FROM a EXCEPT SELECT * FROM b` покажет строки, которых нет во второй.

## Типичные ошибки

### Скалярный подзапрос вернул много строк

`more than one row returned by a subquery` — подзапрос в `=` или в `SELECT` должен давать одно значение. Добавь агрегат, условие на ключ или `LIMIT 1` с сортировкой.

### NOT IN с NULL

Пустой результат там, где строки точно есть, — почти всегда NULL в подзапросе `NOT IN`. Переходи на `NOT EXISTS`.

### Подзапрос в FROM без псевдонима

`FROM (SELECT …)` без `AS t` в старых версиях PostgreSQL — ошибка, а в новых всё равно затрудняет чтение. Всегда давай имя.

### Корреляция не по той колонке

`WHERE x.category_id = category_id` внутри подзапроса — обе колонки берутся из ближайшей таблицы (`x`), условие всегда истинно, и подзапрос перестаёт быть коррелированным. Уточняй внешнюю колонку псевдонимом: `= p.category_id`.

### ORDER BY внутри частей UNION

Сортировка внутри частей ничего не гарантирует: пиши `ORDER BY` в конце всего выражения.

### UNION вместо UNION ALL

Две разные покупки с одинаковыми колонками склеятся в одну, и итог занизится. Используй `UNION ALL`, если повторы — это разные факты.

## Шпаргалка

| Задача | Как написать |
| --- | --- |
| Сравнить со средним | `WHERE x > (SELECT AVG(x) FROM t)` |
| Есть в другой таблице | `WHERE id IN (SELECT id FROM t2)` или `EXISTS` |
| Нет в другой таблице | `WHERE NOT EXISTS (SELECT 1 FROM t2 WHERE t2.id = t.id)` |
| Максимум в своей группе | коррелированный `= (SELECT MAX(…) … WHERE g = outer.g)` |
| Агрегат от агрегата | `SELECT AVG(s) FROM (SELECT SUM(x) AS s … GROUP BY g) AS t` |
| Фильтр по вычисленной колонке | `SELECT * FROM (SELECT …, expr AS e) AS t WHERE e > …` |
| Последняя запись на объект | `CROSS JOIN LATERAL (… ORDER BY ts DESC LIMIT 1)` |
| Больше всех из списка | `x > ALL (SELECT …)` |
| Объединить выборки | `UNION ALL` (с повторами), `UNION` (без) |
| Общие строки | `INTERSECT` |
| Разница выборок | `EXCEPT` |

## Проверь себя

?? Почему `WHERE id NOT IN (1, 2, NULL)` не возвращает ни одной строки?
:: Для любого id условие раскрывается в цепочку `id <> 1 AND id <> 2 AND id <> NULL`. Последнее сравнение даёт NULL, и вся цепочка не может стать TRUE.

?? Чем `EXISTS` отличается от JOIN для задачи «клиенты, у которых есть заказы»?
:: EXISTS вернёт каждого клиента один раз, сколько бы заказов у него ни было. JOIN повторит клиента столько раз, сколько у него заказов, — придётся добавлять DISTINCT.

?? Сколько строк вернёт `SELECT 1 UNION SELECT 1 UNION ALL SELECT 1`?
:: Две. Операции выполняются слева направо: `1 UNION 1` даёт одну строку, затем `UNION ALL` добавляет ещё одну.

?? Как найти среднее число заказов на клиента среди тех, кто заказывал?
:: Агрегат от агрегата через подзапрос: `SELECT AVG(cnt) FROM (SELECT customer_id, COUNT(*) AS cnt FROM orders GROUP BY customer_id) AS t`.

?? Что вернёт `price > ALL (SELECT price FROM products WHERE brand = 'НетТакого')`?
:: Все товары: подзапрос пустой, а «больше каждого из пустого списка» истинно всегда.

?? Почему коррелированный подзапрос может быть медленным?
:: Логически он выполняется для каждой строки внешнего запроса. Если внешних строк сотни тысяч, а подзапрос читает большую таблицу без индекса, работы становится очень много. Часто его переписывают в JOIN с агрегированной таблицей.
